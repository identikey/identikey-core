# Epic 1 Retrospective — Foundation (FR1–FR4)

Epic: 1 – **Foundation**  
Status: completed  
Date: 2025-12-01  
Participants: Bob (Scrum Master), Master Dorje (Project Lead), dev/test personas implicit via story records

---

## 1. Summary

- **Scope covered**: Project scaffold, configuration loading, Keycloak admin client wrapper, error/logging primitives, and connection validation (Stories 1.1–1.5).
- **FRs realized**: FR1 (service account path prepared), FR2 (username/password auth), FR3 (env-based config), FR4 (startup connection validation).
- **Outcome**: The core “vertical slice” for Keycloak connectivity is in place with tests and logging, and both CLI and MCP entrypoints now share a single config + client + validation pipeline.

---

## 2. What Went Well

- **Clean layering and reuse**
  - Config, client, errors, logger, and validation landed exactly where architecture.md and the Epic 1 tech spec said they should live; higher epics can now treat Keycloak as a black box behind `getKeycloakClient()` and `validateConnection()`.
  - CLI (`src/cli/index.ts`) and MCP (`src/mcp/index.ts`) now share the same startup path (load config → validate connection), which removes a whole class of “one interface works, the other doesn’t” bugs.

- **Strong test coverage for the foundation**
  - `config.spec.ts` nails the env/URL/defaulting behaviors.
  - `client.spec.ts` covers singleton semantics and validates the behavior of `validateConnection()` under happy-path, unreachable URL, and bad-credential scenarios using mocks.
  - `errors.spec.ts` and logger tests lock in the error surface and logging behavior, so later services can lean on them safely.

- **Error and log semantics are coherent**
  - `IdentiKeyError` + `ErrorCodes` cleanly separate connectivity (`CONNECTION_FAILED`) from auth failures (`UNAUTHORIZED`) and generic input issues (`INVALID_INPUT`).
  - Logging is centralized via a single Pino logger with sane defaults (JSON in non-dev, pretty in dev), no secrets, and log level from `LOG_LEVEL`.

---

## 3. What Was Hard / Rough Edges

- **Mocking the Keycloak client boundary**
  - Getting realistic-enough mocks around `@keycloak/keycloak-admin-client` and its `serverInfo` probe took some care, especially to simulate “unreachable URL” vs “auth rejected” cleanly in tests.
  - There’s still a bit of coupling between the tests and the Keycloak client’s surface; if upstream types or behavior change, the tests will need attention.

- **Tight coupling between env and test setup**
  - Tests need to juggle `process.env` to cover all config branches; it’s easy to accidentally leak env changes across tests if cleanup isn’t disciplined.
  - There’s no explicit contract test yet that exercises CLI/MCP startup end-to-end (even with mocks); right now we rely on unit tests + intuition that the wiring is correct.

---

## 4. Key Lessons & Insights

1. **Single choke points pay off**  
   Putting all Keycloak connectivity behind `loadConfig()`, `getKeycloakClient()`, `IdentiKeyError`, and `validateConnection()` massively simplifies reasoning and testing; every later service should respect that boundary instead of reaching for env or the raw client.

2. **Validation belongs at the edge, not in the middle**  
   Doing FR4-style connection validation at startup (CLI/MCP entrypoints) keeps failure modes crisp and early, instead of sprinkling “check connectivity” logic around services and tools.

3. **Logging is a product decision, not an afterthought**  
   Getting log structure and redaction right now avoids rework and keeps future stories free to focus on domain behavior instead of log hygiene.

---

## 5. Technical Debt & Risks

- **Real-instance coverage**
  - All current tests are mocked; there’s no checked-in harness that talks to a live dev Keycloak instance and exercises `validateConnection()` + CLI/MCP startup end-to-end.

- **Service-account auth not wired yet**
  - FR1’s “service account” auth path is designed for but not fully implemented; when it lands, config and client logic will need to extend without breaking existing flows.

- **Docs drift potential**
  - Architecture and Epic 1 tech spec currently match the implementation, but they are now “live” contracts; future tweaks to config/client/error/logging behavior must keep those docs in sync.

---

## 6. Preparation for Epic 2 – User Administration

Dependencies from Epic 1 that Epic 2 relies on:

- A stable, tested `getKeycloakClient()` that can be used by UserService and other domain services.
- Reliable `IdentiKeyError` + `ErrorCodes` for wrapping service-level failures.
- Working CLI/MCP entrypoints that already handle config and connectivity before any user-facing tools/commands are registered.

Gaps before going hard into Epic 2:

- Add a lightweight **README section** describing how to configure and run `validateConnection()` (and how to interpret failure logs) so future contributors don’t reverse-engineer it from tests.
- Plan a **future smoke-test harness** against a dev Keycloak instance (even if it’s opt-in for local runs), so we catch regressions in auth/connection early.
