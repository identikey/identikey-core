## Blind pass

The following ten lines were persisted in `reviews/2026-09-24-blind-take.md` before opening design.md, tasks.md, or the delta. They are concerns to answer, not a competing design.

1. Pin Ed25519 for the managed operational Sign+Auth key, with an explicit stored format and a public key that matches the current XID document.
2. Preserve the user's Elect privileges and X25519 wrap target; changing the operational algorithm must not grant the server management authority.
3. Refuse legacy Schnorr blobs explicitly and remint through signup; never reinterpret old bytes as an Ed25519 private key.
4. Accept only a parsed canonical identikey-auth v1 Challenge and return its protocol Response; refuse arbitrary-byte signing and private-key export.
5. Bind fresh A3 or user-held A4 authorization to the exact challenge digest, account, and signing ceremony; neither a cookie nor our Sign key authorizes C2 use.
6. Pin expiry, replay, credential revocation, and one-use authorization behavior, including concurrent attempts and challenge substitution.
7. Persist signing_instruction_authorized before private-key use, correlate completed/failed outcomes, and fail closed when the audit cannot be persisted.
8. Recheck custody and operational-key authority at use so rotation or C2→C3 exit cannot leave a stale signing capability available.
9. Release the Response only to the initiating client; define that binding without turning core into the edge's verifier or an arbitrary callback sender.
10. Tradeoff: fresh challenge-bound consent adds a ceremony and retry complexity, but preserves the C2 privilege boundary while keeping the edge custody-agnostic.

## Comparison and steelman

The author answers the central architectural question correctly: replace only the operational Schnorr key with Ed25519, retain the user's Elect/X25519 key, and use the existing v1 Response. Design decisions 1–4 also expressly reject cookie-only authorization, generic signing, blob export, and challenge-driven network fetches. Reminting old identities is an explicit accepted scope decision. These satisfy the direction of blind concerns 1–5 and 9.

The strongest case for acceptance is that a short design can state security invariants and leave mechanisms to implementation. The tasks already name replay, concurrency, rotation, and response-theft tests. Core also must not duplicate the edge's nonce consumption, identity resolution, or Biscuit issuance. I agree with those limits: no new protocol algorithm, edge verification subsystem, general delegation system, or in-place migration is needed here.

The remaining gaps concern externally observable security behavior, not preferred implementation patterns. The named tests have no definite expected outcome for several races and failures. The following contracts must be reconciled before act.

## Required revisions

### R1 — Pin the actual v1 bytes and validation contract

Design lines 31–34 and delta lines 33–35 say to validate a Challenge's algorithm. At the repository's pinned protocol revision `fd073c0c5cb08f7102e73a4f2b7f9a529210cf98`, `Challenge` contains only `v`, `aud`, `nonce`, `iat`, and `exp`; algorithm belongs to the response/key. Clarify that algorithm validation concerns stored operational-key metadata, without adding a Challenge field.

More materially, pinned `challenge.rs::Challenge::from_bytes` extracts known fields without rejecting additional map entries. The CBOR decoder checks canonical encoding, but `signer.rs::Signer::respond` serializes the parsed struct again. A canonical input with an extra field therefore parses and produces different signed Challenge bytes. Pin exact-byte preservation, for example by rejecting input unless `parsed.to_bytes() == input`, and add that counterexample to acceptance. Define audience syntax, maximum body/nonce sizes, TTL and skew bounds, and the point at which expiry is rechecked after consent. These are local claimant admission rules; they do not authenticate the edge.

### R2 — Make the consent and initiating-client binding implementable

Design lines 40–44 and 51–52 do not define the begin/consent/finish/retrieve contract. Pin the immutable request fields and how account XID, exact Challenge digest, server request id, and client verifier commitment or holder key are associated before authorization. Specify the domain-separated transcript and whether WebAuthn signs that digest directly or authenticates an immutable server-side ceremony bound to it. Existing `ceremonies.rs::finish_assert` returns an XID and optional OIDC authorization; it does not establish a managed-signing instruction.

For A4, identify the accepted proof, account association, and user-held credential authority checks; algorithm or a caller-supplied access-level label alone cannot establish user-held A4. Explicitly reject authorization by the managed operational key. Pin credential revocation and freshness checks, request expiry, and protection against replacing the retrieval commitment after consent. Define routes/message shapes and retrieval behavior so the initiating native client can implement this contract. Add swapped-account, swapped-client-commitment, revoked-credential, and wrong-ceremony acceptance cases. This does not require core to verify the edge's challenge provenance.

### R3 — Define durable authorization, replay, and audit outcomes

Delta lines 60–65 reject an already-completed Challenge, while tasks merely name replay/concurrency tests. Specify the account/challenge replay scope, atomic claim of a pending request, and whether retries return an existing result or fail. Cover concurrent completion, the same Challenge under two request ids, process restart, and failed requests. Edge nonce consumption remains owned by Mjolnir; these rules govern repeated use of the hosted private key.

Specify that the authorization entry is durably committed before key use, not just inserted into a transaction that may roll back afterward. Pin what happens when signing succeeds but completion logging fails, and when the process dies between these steps. A safe outcome must withhold an uncommitted result and prevent a retry from silently reusing authorization; an unresolved authorized attempt must not be falsely described as a known signing failure. Identify how request id and digest are committed to the audit record: current `ConsentAppend` and `ConsentHashInput` have no dedicated request-id field. Require observable failure/retry scenarios rather than only test names.

### R4 — Serialize signing authority with custody changes

Checking the current document before decryption does not close the race: a worker can check C2, another transaction can complete C2→C3 and clear the blob, and the first worker can still sign with material it already loaded. `store.rs::migrate_c2_to_c3` and `apply_document_update_tx` already lock the custody row with `FOR UPDATE`; the new signer must participate in a compatible serialization or fencing contract.

Define the ordering guarantee for signing versus exit, operational-key removal, and credential revocation, including whether a completed but unretrieved Response survives a later exit. Require both race orderings: exit/removal wins and prevents key use, or signing wins and the custody operation observes that ordering. No particular lock implementation is mandated, but the acceptance outcomes must be explicit.

### R5 — Pin the encrypted key format and supported custody rows

Design line 18 leaves storage as “a form the signer can load”; envelope encryption appears only in tasks and the delta. Define version/algorithm discrimination, authenticated account/public-key binding, wrapping-key provisioning and key identifier, and fail-closed behavior for missing/wrong wrapping keys, malformed blobs, swapped blobs, and legacy Schnorr rows. Require the decrypted seed's public key to match the currently authorized operational public before signing. This prevents raw legacy bytes from becoming an unintended Ed25519 seed.

The pinned `SoftwareSigner` provides `from_ed25519_seed([u8; 32])` but no private-key export method. Name the seed-generation/persistence seam and the adapter to the `PublicKeysProvider` required by `c2_native`; verify signup→restart→load→Response against the document key. Keep plaintext lifetime and zeroization obligations explicit for seed copies and signer objects.

Finally, the delta promises C1/C2 responses but provisions only new C2 keys. State which C1 rows can qualify and how supported key material is provisioned, or explicitly narrow this delivery to C2 and track C1. Add the legacy-row rejection/remint scenario to the normative delta, not just the proposal.
