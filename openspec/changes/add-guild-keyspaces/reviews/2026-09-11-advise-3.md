## Blind take (written before design.md / tasks.md)

1. Pin: keyspace id is the genesis `content_hash`; any Postgres row is keyed by it and nothing else. No `guild_id` serial.
2. Pin: `Op.actor` is Ed25519 only. A C2 row (`c2_native` + `PrivateKeyBase`) carries Schnorr + X25519, so no C2 key can author or admin. Who holds the admin Ed25519 must be named, and if core holds it that is C1-shaped guild custody and must say so.
3. Pin: the C2 wrap-target is the X25519 encapsulation half as-is. §7.2 conversion does not apply (there is no Ed25519 to convert). Protocol §6 admits `ed25519` / `p256` only, so until `ikp-2l8` a C2 PUK cannot sit on a `RosterEntry`. The design must say exactly where the interim recipient lives and that it is not a fork of §6.
4. Refuse: local `PublicKey.alg` values not in the standard; `guild.*` kinds; `guilds` OIDC claim; any edit to `managed-custody`; join as an `authorize_elect` write.
5. Pin: signup drops the user private, so a wrap to a C2 recipient is unwrappable by anyone today. The change must say this plainly so nobody reads "member" as "can read secrets".
6. Pin: concurrent `epoch-begin` is stored, applied by neither, surfaced. Core never picks a winner.
7. Pin: passkeys are `credentials` rows, never PUKs (WebAuthn gives no ECDH). Already in the proposal; keep it.
8. Pin: `profile` is an opaque tstr in core. Epoch policy is runtime, not this node.
9. Tradeoff: ship the mapping now with an interim wrap-only recipient vs wait for `ikp-2l8`. Shipping is fine only if runtime is apply-only and wrap emission is behind the errata.
10. Exit test: a guild whose PTK is wrapped only to keys nobody can use passes trivially but is worthless. Fine as a bookkeeping step; not fine if presented as data access.

## Steelman for send-back

**"A wrap whose recipient sits on no roster entry is a member the
protocol never named. That is a fork by omission."** Rejected. §7
`Wrap` does not bind `recipient` to a roster `puks` entry. §9
`LeaveBody.recipient` and `ChangeBody.blacklist` already address a
recipient key without an actor, so a recipient-keyed identity is a
protocol notion. The gap is a missing `alg` spelling on §6, which is
exactly what `ikp-2l8` closes, and this change refuses to construct
the entry rather than guess. That is the honest interim, bounded by
a bead with acceptance criteria.

**"Runtime genesis then cannot be exercised with any row this store
produces; the tests will use synthetic Ed25519 actors."** True, and
correct. The day-one house admin is a user-held Ed25519 by ADR-012
§4 "Actor"; this store holds no such key and must not mint one
(ADR-010). Synthetic actors in tests are the consequence of not
doing custody creep, not a defect in the mapping.

**"Accept ships an inert feature."** Accepted as fact, not as a
block. Take item 10: a keyspace whose only recipients cannot unwrap
is bookkeeping. ADR-012 §4 "Live instance" and the delta say this
out loud and forbid the tempting fix. Runtime is apply-only.

## Notes (body only, not blocking)

- Delta line 157, scenario "Kick without waiting for rotation":
  "request-to-bytes for that member is denied". Carried from advise-2.
  This crate denies against the applied roster / blacklist; runtime
  design.md already says it does not serve bytes. Fix at fold or in
  the runtime act; not an architecture question.
- Delta wrap-target requirement: "A row whose user private is not
  held by the user". After `signup` the private is held by no one.
  "not held by anyone" is the precise phrase; the following clause
  ("until that private is user-held") already carries the intent.
- ADR-012 §4 says PUK rotation of the encapsulation key is an Elect
  rewrite. Note for the wallet / export path, not this change:
  `PrivateKeyBase` derives both halves from one seed and bc-xid keys
  a `Key` on the whole `PublicKeys`, so rotating the encapsulation
  half alone means composing `PublicKeys` from separate parts or
  replacing the user's Elect key too. Either way it is an Elect
  rewrite, so the ADR sentence stays true.
- Proposal "What" says "Today's C2 rows are wrap-target-only". At
  HEAD the precise state is "wrap-recipient-only and absent from the
  roster". design.md and ADR-012 say the precise thing; the proposal
  summary is loose but not wrong.

## Verdict

Accept. Fold is unblocked for `add-guild-keyspaces`. Runtime
(`add-keyspace-runtime`) and the protocol errata (`ikp-2l8`) stay
their own boxes.
