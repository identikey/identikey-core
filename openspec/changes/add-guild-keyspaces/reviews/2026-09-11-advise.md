## Independent take (written before design.md)

1. Pin: the PUK for a C2 member must be a concrete key in the stored
   document. Signup generates the user's Elect key server-side and
   drops it; the passkey is P-256 WebAuthn and cannot ECDH.
2. Pin: C1 rows have no user key; they cannot be wrap-target members.
3. Pin: the roster `actor` is raw 32-byte Ed25519. Say which bytes of
   a bc-components `PublicKeys` go there, or say none do.
4. Refuse: `managed_key_blob` as wrap-target or actor.
5. Refuse: cache-only membership state not derivable from the log.
6. Refuse: picking a winner on concurrent `epoch-begin`.
7. Pin: `revoke_device` untouched; the FOKS cascade is vacuous for
   passkeys because a passkey never holds the PUK.
8. Pin: if the PUK lives in the XID document, PUK rotation is an Elect
   rewrite. Join is not; rotate is. Own it.
9. Tradeoff: reuse the user's document key as PUK (one key, but a
   guild-decrypt compromise is an Elect compromise) versus a separate
   user-held PUK (needs a home and a rotation story outside the doc).
10. Pin: no `identikey-log` dependency exists in this workspace yet.

## Why send-back: the PUK and actor selectors select nothing

ADR-012 §4, design.md "C2 mapping", and the delta requirement
"Wrap-target is the latest PUK" all say the wrap-target is the
member's current identity key, **Ed25519 via X25519, or P-256**. The
roster `actor` is **raw 32-byte Ed25519**.

Now apply that to the only C2 document this crate can produce.
`c2_native` (`privilege.rs:118`) takes a `PublicKeysProvider`; the
production `signup` handler (`identikey-server/src/main.rs:406`)
passes `PrivateKeyBase::new()`. In bc-components 0.31 the default
`public_keys()` is `schnorr_public_keys()`: a **BIP-340 secp256k1
Schnorr** signing key plus an **X25519** encapsulation key. So on
every stored C2 row:

- The user's Elect key is Schnorr. It is not Ed25519 and not P-256.
  Under the ADR's own words it is not a wrap-target and it cannot be
  an `Op.actor`. "At C2 it usually is the PUK" (design.md, runtime
  design "PUK selector", advise2 "implementer gaps") is false for
  every row in this store.
- The user's private key is dropped at the end of `signup`. Nobody
  can unwrap to it even if it were chosen. Elect-key export is a
  named future surface, not this one, and the ADR does not say the
  mapping is inert until it exists.
- The passkey (`credentials.cose_public_key`, P-256) is the only key
  the user holds, and the design correctly rules devices out. WebAuthn
  never exposes ECDH, so it could not unwrap anyway.
- IdentiKey's Sign+Auth key is the only usable key on the server side
  and it is the one the ADR forbids. That is the right refusal. It
  leaves the runtime with no lawful recipient.

The 2026-09-01 send-back item 3 asked for the C2 privilege split to be
mapped onto PUK. The amend answered with "not automatically a
wrap-target unless it is also the PUK", which is circular. A mapping
ADR that names curves no stored document carries has transcribed the
protocol, not mapped it. `add-keyspace-runtime` is already ACTIVE
BUILD on this premise; an implementer will either reach for the
managed blob or silently change the C2 key scheme. Both are
architecture decisions and belong in this change, not in act.

Steelman considered: "identity keys already specified" in protocol
§2.1 lets the ADR defer the concrete key to the identity spec, and
the runtime can select bytes. Rejected, because the identity spec as
implemented here yields Schnorr+X25519, and the ADR affirmatively
names other curves. The gap is inside the ADR's own text.

## Owed (added to tasks.md)

1. **Name the C2 PUK against the stored document.** Either (a) the
   user's X25519 encapsulation half of the `PublicKeys` already in the
   XID document is the PUK, in which case ADR-012 §4 and design.md
   must say "X25519 encapsulation key" rather than "Ed25519 via
   X25519", and note that protocol §5 lists only Ed25519-derived
   X25519 and P-256 (the §7 alg table accepts a raw X25519 u-coord; if
   §5 needs an errata line, that is the protocol repo's box); or (b) a
   distinct user-held PUK, introduced by a named change. Under either,
   state that C1 rows and any row whose user private key is not held
   by the user have no wrap-target and cannot be members, and that
   PUK rotation for a key living in the XID document is an Elect
   rewrite via `apply_document_update`.
2. **Name the Ed25519 actor for a member of this store.** A Schnorr
   user key cannot author `keyspace.*` ops or be admin. Say where the
   admin companion lives. If the A4 `identikey_auth`
   `device_public_key` (Ed25519, user-held) is excluded because
   devices are not keyspace objects, say so and name the alternative
   (wallet-held key, or a second Ed25519 key in the document).
3. **State the live-instance premise.** Signup drops the user's Elect
   private key. Until a user-held key exists (Elect export or wallet
   surface, named), no C2 row can unwrap. Amend the runtime design's
   "at C2 it usually is the PUK" to match, so act does not proceed on
   a false premise.

## Notes (body only, not blocking)

- Cascade §5: for passkey devices the FOKS cascade is vacuous, since a
  passkey never holds PUK material. Worth one sentence so a later
  reader does not add a "rotate PUK on passkey revoke" trigger.
- The tradeoff in take item 9 is unresolved by the change and is the
  real choice behind owed box 1. Reusing the document key makes guild
  decrypt compromise equal Elect compromise; a separate PUK avoids
  that but needs its own home. Either is acceptable; pick one.
- Design C2 table row "Latest PUK (Ed25519 or P-256)" is a separate
  row from "User Elect" with no third key in the document to point at.
  That is the visual symptom of the gap above.
- `identikey-log` is not yet a workspace dependency; runtime takes it
  as a git-dep. Fine.
