## Blind take

1. Pin the library ceremony to an existing account identity; successful recovery must never select a new XID.
2. Pin verification to the factor already authorized for that account, with explicit ownership of the directory lookup.
3. Refuse any public constructor or restoration path that turns an unchecked assertion into account recovery authority.
4. Pin the exact transition that spends a valid factor; concurrent submissions must produce at most one authority grant.
5. Require challenge state, attempts, expiry, and consumption to share a coherent commit boundary, including failure behavior.
6. Require cryptographically generated secrets and opaque identifiers; caller-controlled predictable values cannot carry recovery authority.
7. Pin proof scope, lifetime, and consumption so replay cannot create another acceptance or extend authorization indefinitely.
8. Preserve hosted email verification and replacement-passkey behavior, including the prohibition on recovery-session signing and key minting.
9. Refuse a parallel hosted token store or implicit takeover of hosted recovery by this library-only ceremony.
10. Tradeoff: an injected delivery/storage boundary is reasonable, provided its trust and atomicity obligations are explicit and testable.

This ten-line take was written to this file before opening the delta, design, tasks, or previous review. Inputs were the proposal's Why and the living account-recovery spec; the packet supplied no code citations. Source inspection followed the blind pass.

## Comparison and steelman

The amended contract answers most of the take without expanding scope. Caller-supplied ports, trusted integration callbacks, and deferred hosted wiring are appropriate. The corrected Why accurately distinguishes the missing library ceremony from existing hosted recovery. I do not require a production store, transport, route, proof TTL, or a cryptographically random challenge identifier: unpredictable secrets plus collision-safe identifiers meet the generation concern. The blind take's stronger identifier preference is not an additional gate.

The strongest argument for acceptance is that finish establishes a trusted, immutable account binding, while acceptance rechecks the bound account's current custody and spends the proof. That can be a coherent design if finish deliberately freezes destination authority. Conversely, a design that treats directory removal or reassignment as revocation would revalidate the binding at acceptance. Both policies can preserve the bound XID; the missing decision is whether the outstanding proof survives that directory change. This was explicitly owed under R2 in the previous review, rather than a new implementation preference.

## R1 — Answered: one committed factor transition

`design.md:75-84` and delta `specs/account-recovery/spec.md:119-138` now put expiry, attempt state, and consumption in one conditional committed transition. Only committed consumption produces a proof; store failure does not. Two successful presentations have one winner, and a fifth committed SMS failure defeats a competing success. Failed writes do not spend attempts. This supplies the missing store-port obligation; concurrent wrong attempts must obey that same transition rather than read/modify/write independently. Adapter race and error coverage remains implementation work under the existing task commitments.

## R2 — Still owed: binding changes between finish and acceptance

The trusted lookup, supplied-XID mismatch refusal, immutable channel/destination/purpose/XID binding, bootstrap destination provenance, and callback inputs are now explicit (`design.md:88-97`; delta `specs/account-recovery/spec.md:142-161`). Trusted callbacks must use those inputs, which adequately addresses target substitution without pretending to sandbox callback code.

However, `design.md:92-94` expressly addresses unbinding/rebinding **before finish**, and the delta's refusal is also confined to finish. Acceptance checks current C1/C2 custody (`design.md:58-60`; delta `specs/account-recovery/spec.md:73-79`), but does not specify whether it checks the destination-to-XID relationship again or deliberately relies on the relationship captured at finish.

Concrete sequence: destination D belongs to XID A; finish succeeds and returns a recover proof; D is then removed from A or reassigned to B; A remains C2; the old proof is presented to `accept_recover`. The existing custody check still passes for A. An implementation can invoke the callback for A using the snapshot, while another can refuse because the directory no longer binds D to A. The contract does not choose between these authorization outcomes.

Owed: explicitly choose the post-finish policy and align design, delta, and tasks. If acceptance revalidates, specify refusal and proof disposition on unbinding/rebinding. If finish intentionally freezes destination authority, state that later directory changes do not revoke this proof, explain that boundary, and retain the current-custody and single-use checks. Add acceptance scenarios for both removal and reassignment after finish, including the expected callback count and proof disposition. This does not require a transaction spanning the directory and caller closure, or any hosted integration.

## R3 — Answered: acceptance consumes proof; restore_access cannot authorize

`design.md:101-107` and delta `specs/account-recovery/spec.md:165-175` require single acceptance, consumption even on callback error, removal of public `granted()`, and no alternate authorization through `restore_access`. The explicit non-authorizing result in delta line 115 resolves the older statement that this function accepts the proof and returns no key bytes. Returning a compatibility `ManagedAccess` marker is consistent only if it grants no authority, as the amendment now requires.

The current implementation still derives `Clone + Copy` and exposes `granted()` (`crates/identikey-recovery/src/lib.rs:76-90`), and `restore_access` still returns the marker unconditionally (`lib.rs:93-102`). Those are expected implementation obligations, not reasons to reject this pre-implementation contract. The new semantics must hold across all ordinary duplication and construction paths; the existing R3 commitment includes bypass and duplicate-acceptance coverage. Current-custody checking at acceptance remains required independently of the R2 destination-policy decision.

## R4 — Answered: cryptographic generation

`design.md:111-116` and delta `specs/account-recovery/spec.md:179-189` now require cryptographic email/SMS generation, unbiased six-digit sampling including leading zeros, collision-safe insertion, and failure without issuing a factor or secret. The design also pins unambiguous hash-input lengths. These are sufficient contracts for the requested library implementation; focused entropy/error/collision tests remain owed during act, not in this review.
