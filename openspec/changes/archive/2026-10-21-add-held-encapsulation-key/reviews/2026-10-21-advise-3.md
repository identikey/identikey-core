## Blind take (written before opening design.md, tasks.md, or earlier reviews)

1. Pin: seal only `PrivateKeyBase::x25519_private_key()` (HKDF "agreement" output). Never seal the base seed; that derives the Schnorr Elect key and turns C2 into C1.
2. Pin: a new column with its own AEAD domain and AAD (xid ‖ user X25519 public). It must not reuse the `identikey-managed-key-v1` AAD, so a blob moved between columns fails closed.
3. Pin: open checks scalar→public == `c2_wrap_recipient(current doc)`. A PUK rotation (Elect write) strands the held scalar and must fail closed or NULL it.
4. Pin: `migrate_c2_to_c3` NULLs the held scalar in the same UPDATE. If the climbed doc keeps that X25519 public, say plainly that we once held it.
5. Pin: rows from before this change stay NULL. Do not backfill or remint silently, because the private was dropped.
6. Pin: unwrap clamps per §7.2, rejects zero/small-order, uses the §7.1 blake3 KDF, zeroizes. No HTTP route reaches unwrap.
7. Pin: export needs a fresh A3/A4 consent like the responder, not the cookie. It takes the same custody FOR UPDATE lock with rung/blob rechecks, so exit and revoke win races. No ACAO from `spa_cors`. `no-store`.
8. Refuse: any wording that keeps "we never had the user's private key" or "inert until user-held". The living specs (guild-keyspaces wrap-target req; architecture §4 "Live instance") must be MODIFIED, not left contradicting.
9. Refuse: wrapping to `managed_key_blob`, or the operational companion X25519, as a shortcut.
10. Tradeoff: this makes C2 confidentiality custodial (IdentiKey can read what is wrapped to the user). It buys live decryption. The exit test then depends on export existing, not only consent wording.

## Steelman against my take

- **Climb requires an export first (I only asked for a null).** At first this
  looked like friction on the exit path. The other order is worse: climb nulls
  the only copy of a key that already has wraps addressed to it, and the user
  loses data. Hosted C2 users cannot climb today in any case, because Elect was
  dropped. So the gate only constrains wallet and test paths, and there it
  protects the exit test ("leave with keys and data"). The contract's choice is
  better than mine.
- **Null on recipient rewrite, rather than only failing at open.** Nulling
  stops a key from sitting in the row with no use. A stale seal could still
  open wraps made to the old public before the rotation. Under §8, the old-PUK
  wraps belong to old epochs, so the user loses old-epoch access through
  IdentiKey after a rotation. That is the honest result of rotating a key we
  never got the replacement for. It is acceptable, and the contract states it.
- **Library-only unwrap with an HTTP `begin` for purpose `unwrap`.** HTTP can
  create an `unwrap` row that HTTP cannot finish. That is harmless. The row
  expires in 5 minutes and has a single use. It also gives
  `add-recrypt-proxy-vm` a begin row to reuse.
- **Same managed wrap key for `IKMK` and `IKEK`.** One operator secret now
  opens both Sign and decrypt material. The other choice, a second env key,
  doubles boot fail-closed surface and rotation work. Domain separation
  through the AAD tag is the right cost here, given "do not rotate". The
  contract states that the gate is policy.

## Notes (non-blocking; for the implementer)

- **N1. A4 signature form is not pinned. Defer A4 here rather than guess.**
  The transcript bytes are pinned. The A4 signature is not: which algorithm,
  whether the message is the raw transcript or its SHA-256, and what proof
  encoding the library receives. On a `c2_native` document the Elect key is
  BIP-340 Schnorr. The responder's A4 accepts only an Ed25519 identikey-auth
  Response (`managed_challenge.rs:869`), so copying it makes A4 dead for every
  hosted document. No producer exists in this change. My recommendation: make
  finish and unwrap refuse A4 with a named "A4 not accepted in this change"
  error, and test that refusal. Leave the A4 wire form to the wallet change.
  If the implementer does build A4, write the chosen form into the delta
  before coding. A test-only A4 format should not become the wallet contract
  by accident.
- **N2. Preflight.** `spa_cors` answers `OPTIONS` itself and returns before
  `next.run` (`main.rs:185-189`). If the exemption is "skipped by path", the
  skip has to come before that early return. Merging the two routes after the
  `.layer` call handles this on its own. Extend the SPA-origin test to send an
  `OPTIONS` preflight as well as the `POST`.
- **N3. Climb disclosure.** If the climbed C3 document keeps the same X25519
  public, IdentiKey did hold that scalar under the managed wrap key, including
  in database backups taken before the climb. Nulling the column does not
  reach those backups. Add one sentence in the ADR-012 amendment: rotate the
  encapsulation key after climb if the backup window matters. Do not add a
  climb rule for it.
- **N4. Scalar handling.** Unwrap uses the stored 32 bytes as a native X25519
  scalar (clamp per RFC 7748, as `x25519` does internally). It must not pass
  them through an Ed25519 secret-key map (§7.2 last paragraph). One test
  should derive the public from the opened scalar and compare it to
  `c2_wrap_recipient`. That is the Decision 2 open check, so it adds no extra
  cost.
- **N5. Passkey user verification.** Export hands over a long-lived decryption
  key. Use the same webauthn-rs `start_passkey_authentication` path as the
  responder (`ceremonies.rs:214,340`). That passkey ceremony requires UV. Do not
  build this begin on a discoverable or security-key API that would relax UV.
- **N6. Seal with no remaining credential.** If every passkey is revoked, the
  seal stays at C2 with no way to consent to anything. The proposal already
  rules a "forget" purpose out of scope. Name that leftover state in the
  ADR-012 note so it is a known state, not a surprise.

## Verdict

Accept. On the architecture questions, the contract makes the right call:
which private is held, how it is kept apart from Sign material, what the
consent gates and in what order, the interaction with exit, and the honest
custodial statement. I found no gap that would make an implementer pick
wrong live behavior. N1 is the closest. Its live path (A3) is unaffected, and
the safe default is stated above. Act may proceed once the conductor's gates
allow it.
