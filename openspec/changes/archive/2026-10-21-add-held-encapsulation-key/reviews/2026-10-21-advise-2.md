## Blind take (written before opening design.md, tasks.md, or the first advise)

1. Pin: seal only `PrivateKeyBase::x25519_private_key()` (one-way derived), never the base bytes. The base bytes also derive Schnorr Elect, so sealing them would put Elect on our side and break the C2 split and the C3 climb's rule that some key we do not hold can Elect. Add a test that the held blob cannot produce the document's Elect public.
2. Pin: this needs its own envelope with its own magic and AAD domain, not IKMK or `identikey-managed-key-v1`. The AAD must bind the XID and the published X25519 public. On load, check that the scalar's public equals `c2_wrap_recipient(doc)`, and fail closed if it doesn't.
3. Pin: signup persists the held key in the same transaction as `create_managed`. Rows from before this change stay inert, because there is nothing to backfill.
4. Pin: exit C2→C3 destroys the held key in the same UPDATE that NULLs `managed_key_blob`. An Elect rewrite that changes the X25519 public makes the held scalar stale. Specify what happens to it.
5. Pin: unwrap is an in-process library call with no HTTP route. `spa_cors` wraps the whole router, so any new route is CORS-reachable.
6. Pin: export is its own consent with its own domain tag. Unwrap must neither need nor imply export.
7. Refuse: making `managed_key_blob` or the operational X25519 a wrap-target, and reusing the IKMK type for a second key kind.
8. Refuse: leaving the living guild-keyspaces "inert until user-held" scenario, ADR-012 item 4 "Live instance", and the `c2_native` "never had the user's private key" comment silently false.
9. Ask: who authorizes an unwrap? Is it unattended, or gated by fresh A3/A4 like Sign? Is that recorded in the consent log?
10. Tradeoff: holding the scalar makes recordings openable, but it turns us into a decryption-capable custodian of every PTK wrapped to a C2 user. A leak of `IDENTIKEY_MANAGED_WRAP_KEY` would then expose content, not just signing. Weigh a separate KEK/kid and consent-gated unwrap against unattended pipelines.

## Compare and steelman

- **1, answered.** Decision 1 is exact. It keeps the derived scalar, does not
  keep the base or Elect, and the open check (derived public equals the
  current `c2_wrap_recipient`) would catch base bytes sealed by mistake. I
  would still like the Elect-not-derivable test named, but the open check
  covers the same mistake.
- **2, answered.** Decision 2 specifies `IKEK`, the
  `identikey-encapsulation-key-v1\n` AAD over XID and recipient, the magic
  rejected in both directions, and the public checked again on open.
- **3, answered.** The design says to seal before `create_managed`, that a
  failure leaves no row, and that there is no backfill.
- **4, half answered.** Climb nulls the seal in the same UPDATE, and it
  refuses until an export is logged (the N4 option, taken). The contract
  does not say what a PUK rotation does to the seal. The open check fails
  closed in that case. That is the right behavior, and it also means a
  rotation revokes our access to wraps for the new public. Say it in one
  line (N-a).
- **5, answered** for unwrap. Export is a route that sits outside
  `spa_cors` and sends `no-store`. Nothing yet tests that the route is
  really outside the layer (N-b).
- **6, answered.** It has its own domain tag and purpose field, and the
  managed-challenge consent is refused.
- **7 and 8, answered.** The guild-keyspaces delta and the ADR note state
  the custodial-read fact in so many words. That was the hard part of
  advise 1, and it landed well.
- **9, the gap.** Unwrap is consent-gated and audited, which is the answer
  I wanted. But how an `unwrap` consent row goes from begun to consumed is
  not defined, and the consent is not tied to the wrap it opens. These are
  B1 and B2 below.
- **10, steelman.** The design argues that C2 already puts Sign under this
  keyring, that a download-only key dies with the browser, and that Duke's
  bounds say "IdentiKey is the encryption key". I accept that. A separate
  KEK would only help against an operator who holds one env var and not the
  other, and that is not a realistic split on one guest. Per-operation A3
  unwrap rules out unattended pipelines. That is right for "the owner mints
  a recryption key later", which is user-present. I am not asking for a
  second KEK.

## Blocking (send-back)

**B1. `unwrap` consent has no finish step.** The design says "Hosted finish
is only `POST /account/encapsulation/export`" and "Library unwrap consumes a
finished `unwrap` row". The delta's unwrap inputs are "a consumed consent row
whose purpose is `unwrap`". Nothing verifies the A3 assertion (or A4
signature) for an `unwrap` row. There is no route for it, and no library
function is named that takes the proof. As written, "finished" and "consumed"
are states that no specified code produces. That leaves an implementer two
bad options:

- treat a *begun* row as sufficient, which drops the proof entirely, or
- add an unnamed finish that marks a row finished in one transaction while
  a later unwrap consumes it in another. A finished but unconsumed row is
  then a bearer token for one decrypt.

Pin one shape. My recommendation: the library unwrap takes the A3 assertion
or A4 signature itself. In one transaction it verifies the proof against the
stored row, rechecks the row (expiry, purpose, unused), marks it used, opens
the seal, unwraps, and writes the audit. That is the same atomicity export
already has, because export's POST is the finish. Also say that this change
has no live caller of unwrap. Tests exercise it, and the first production
caller is a named later change (the recryption-key mint). Otherwise the
proposal's "Working: a new account unwraps a data key after the creating
process is gone" reads as a live capability.

**B2. The `unwrap` consent is not bound to the wrap it opens.** The
transcript is `domain || purpose || XID || attempt id || WebAuthn challenge
|| iat || exp`. Nothing in it names the wrap. One A3 tap for "unwrap" can
then open whichever PTK or data key the library caller presents: a house
keyspace PTK, or a different recording. The audit row
`encapsulation_unwrap` cannot say what was opened. The responder binds the
exact Challenge bytes, and advise 1's B1 was "the consent is not bound to
anything". That is still true one level down. Pin the following:

- For purpose `unwrap`, begin takes the Wrap (or its canonical CBOR
  digest) and stores it. The transcript carries that digest, so A4 commits
  to it. For A3 the binding comes from the stored row.
- Unwrap refuses a wrap whose digest differs before decrypt.
- The consent-log entry records the digest (and the keyspace id and epoch,
  when the caller has them).
- Add a scenario: a consent begun for wrap W does not open wrap W′.

Begin for `export` keeps the current transcript.

## Owed, non-blocking (fix while you are in there)

- **N-c. Transcript bytes and vector.** Purpose, attempt id, challenge, and
  `iat`/`exp` have no encoding yet: fixed width or length-prefixed, UUID as
  16 raw bytes or as text, u64 BE. No hash or digest vector is given. The
  managed-consent precedent pins both, with digest
  `7efc1d28…` in living managed-custody. A4 is not live, but the "later
  wallet" the design reserves A4 for needs exact bytes. Pin the encoding
  (with B2's wrap digest) and one fixed digest vector, and add a scenario.
- **N-d. Revocation and exit race.** The responder rechecks the custody row
  and the credential row under `FOR UPDATE` locks that `revoke_device` and
  climb also take (`managed_challenge.rs:866`, `:944`, `:965`; living
  "Revocation wins" / "Exit wins the race"). Export and unwrap rely on a
  passkey, and the contract does not require that recheck. A passkey revoked
  between begin and finish could still export the scalar. Require the same
  lock pair immediately before decrypt, and add a "Revocation wins"
  scenario for export.
- **N-a. Rotation.** Add one sentence: after an Elect rewrite changes the
  user X25519, the open check fails closed and IdentiKey can no longer open
  wraps addressed to the new public. Since the old seal is now useless,
  decide whether the rewrite nulls the seal or leaves it.
- **N-b. CORS test.** `.layer(spa_cors)` wraps the whole router
  (`main.rs:162`). "Outside `spa_cors`" means the routes are merged after
  that layer, or the middleware skips the path. Make the export task
  include a test showing that a registered SPA origin gets no
  `Access-Control-Allow-Origin` on begin or export.

## Notes for Duke (not owed)

- **No forget path.** A hosted row has no Elect, so it can neither rotate the
  X25519 nor climb. Export leaves the server copy in place. After this
  change, a hosted user who exports and leaves still has IdentiKey able to
  open anything later wrapped to that public. Under the narrowed exit test
  this is not capture: the user leaves with the key and the data. It is,
  however, a confidentiality fact the user cannot undo. A later
  `purpose: destroy` (A3, it nulls the seal, and it is logged) would make
  leaving clean. Consider naming it as a follow-up change. Not blocking
  here.
- **Who performs export A3 live.** The proposal has no new page, and a
  WebAuthn assertion for RP ID `auth.identikey.me` needs a client on that
  origin, or a native app with an associated domain. The responder has the
  same "no hosted page" shape. Export is the exit path for the
  encapsulation key, so say which client the owner uses today. If none
  exists, name the change that adds an `/account` export button.

## What is good

The key choice, the envelope separation, the cross-rejecting magic, and the
open-time public check are exact and cheap. The guild-keyspaces delta now
states the custodial read plainly, including house PTKs, instead of leaving
"inert" in place as a false comfort. Requiring export before climb is a
neat use of the audit that B4 added. Out of scope stays disciplined: no
PRE scheme, no Blob Door, no recrypt VM, no Elect retention. Once B1 and B2
are pinned, the tasks order is buildable as is.
