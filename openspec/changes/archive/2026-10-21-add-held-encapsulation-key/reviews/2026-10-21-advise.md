## Blind take (written before opening design.md / tasks.md)

1. Pin: seal only `PrivateKeyBase::x25519_private_key()`, the 32 bytes HKDF
   derives. Never seal the base bytes. bc-components 0.31.1 derives the
   Schnorr Elect key from those same bytes, so sealing the base hands
   IdentiKey Elect.
2. Pin: a separate blob, column, and AAD domain from `managed_key_blob`
   (purpose tag, XID, X25519 public). Each loader refuses the other's blob.
   Say whether it shares `IDENTIKEY_MANAGED_WRAP_KEY`.
3. Pin: opening needs consent, as the responder does: a fresh A3, or an A4
   Elect proof bound to this request. A cookie is not enough. Before
   decrypt, recheck that the public is still `c2_wrap_recipient`.
4. Pin: amend the living text this change reverses: ADR-012 item 4
   "Live instance", guild-keyspaces "unwrap SHALL fail until that private
   is user-held" and its inert scenario, and the `c2_native` claim "We
   never had the user's private key".
5. Pin (exit test): climb must not strand data. Either the user can export
   the X25519, or a PUK rotation and rewrap must happen before the blob is
   destroyed.
6. Pin: older rows have no seal and stay inert. No backfill.
7. Refuse: the held key acting as a §6 actor, an admin, or a signer, and
   any "decrypt for the caller" route that hands plaintext or the PTK to
   an RP without the ceremony.
8. Refuse: wrapping to `managed_key_blob` or to the operational X25519 that
   signup discards.
9. Tradeoff: holding the encapsulation private makes C2 confidentiality
   custodial. The operator, or anyone with the DB and the wrap key, can
   read whatever is wrapped to the user. The gain is recordings that open
   on a live account. That cost has to be written into the custody
   semantics, not left as an implementation detail.
10. Ask: who calls unwrap, and does the unwrapped data key ever cross the
    wire?

## Compare and steelman

The author answered most of the take.

- **1, answered.** Decision 1 keeps "the X25519 scalar … whose public
  equals `c2_wrap_recipient`", and Decision 2's open check (derived public
  equals the current `c2_wrap_recipient`) catches a sealed base: base
  bytes used as an X25519 scalar give a different public. Elect/Schnorr is
  named as not kept.
- **2, answered, with one gap.** It gets its own column
  (`encapsulation_key_blob`), its own magic (`IKEK`), and the same keyring,
  stated, with no rotation. Each opener rejects the other's magic. The gap
  is that the AAD domain tag is not named (see N1).
- **3, partly answered.** It forbids the cookie and refuses the managed key
  as A4, and the open-time public check doubles as the C2 recheck, because
  `c2_wrap_recipient` refuses non-C2. It does not say what the consent is
  bound to (B1).
- **4, partly answered.** ADR-012 is amended. guild-keyspaces is not
  (B3).
- **5, answered.** Export exists under the same consent, so the user can
  leave with the scalar. Climb destroying the server copy is then a
  convenience question, not capture. That fits Duke's narrowed exit test.
  See N4 on ordering.
- **6 and 8, answered** explicitly.
- **7, partly answered.** It says it is not a signer and not PRE. The
  hosted unwrap surface is unclear (B2).
- **9, steelman.** "Why the server also holds it" argues that C2 already
  means the operator holds Sign under the same wrap key, and that a
  download-only key would die with the browser. I accept this as a
  decision. Duke's bounds ("IdentiKey is the encryption key") back it.
  But Sign custody lets the operator impersonate going forward.
  Encapsulation custody lets the operator read everything wrapped to the
  user, past and future, including house PTKs. That is a new axis, and
  the living specs have to say so (B3).

## Blocking (send-back)

**B1. The consent for opening the seal is not bound to anything.** The
delta says "a fresh A3 WebAuthn assertion bound to that attempt" and the
design says "a completed A3 or A4 proof for this export". Neither names:

- a begin step that mints the WebAuthn challenge (or the A4 consent
  Challenge),
- a consent transcript with its own domain tag and a purpose field
  (`export` vs `unwrap`) that cannot collide with
  `identikey-managed-consent-v1\n`,
- single use, an expiry, and what binds the proof to the account.

Without these, the design text "uses the A3 and A4 checks the challenge
responder already applies" invites reusing the responder's consent. A
proof captured for a managed-challenge or session-bind attempt could then
open a scalar export. Export is the most sensitive operation in this OP:
it is an irreversible disclosure of a decryption key. Pin the state
machine (begin/finish, or begin/consent/finish/retrieve with PKCE as the
responder has), the domain tag and purpose, single use, expiry, and a
scenario where a responder consent is refused at export.

**B2. The hosted unwrap surface is ambiguous.** The ADDED requirement
says "A hosted unwrap or export SHALL accept only …", and the proposal's
journey says "Export and unwrap are a consent-gated HTTP call". Only
`POST /account/encapsulation/export` is named. Decide one of these:

- (a) In this change, unwrap is library-only (store + keyring + XID +
  wrap + consent proof) with no HTTP route, and the data key never leaves
  the process.
- (b) There is a hosted unwrap route. Name it, say who receives the
  32-byte data key, and confirm it gets the same B1 binding.

Right now an implementer could ship a route that returns data keys to any
caller that holds a proof.

**B3. The living guild-keyspaces spec contradicts this change.** The
"Wrap-target is the user's X25519 encapsulation key" requirement says
"unwrap SHALL fail until that private is user-held (inert on purpose …)",
and the scenario "C2 wrap is named and inert until user-held private"
expects failure "until Elect export or a wallet holds the private". After
this change, a new C2 row's private is held by the server, not by the
user, and a consenting process can unwrap. There is no delta for
`guild-keyspaces`, so after folding, the two living specs disagree.

Add a MODIFIED guild-keyspaces delta. It should say that new C2 rows can
unwrap through the held seal under consent, that older rows stay inert,
and that `managed_key_blob` is still never a wrap target. In the same
delta and in the ADR-012 amendment, state the confidentiality
consequence: IdentiKey can open a PTK wrapped to a held C2 member,
including in house keyspaces.

**B4. No audit trail for opening the seal.** The responder writes a
completion audit commit. Export and unwrap of a decryption key write
nothing in this contract. Require a consent-log entry (A3/A4 proof,
`action` = `encapsulation_export` / `encapsulation_unwrap`) and a custody
event on success, plus a scenario.

## Non-blocking (fix while you are in there)

- **N1. AAD domain.** Name a distinct AAD tag for `IKEK` (for example
  `identikey-encapsulation-key-v1\n` || xid || recipient). Do not reuse
  `identikey-managed-key-v1\n`. The magic byte is not under the AEAD.
  Today only the differing public separates the two envelopes.
- **N2. Small-order checks.** Say which input the check applies to. The
  attacker controls the wrap's `ephemeral`, not the stored recipient.
  Reject a small-order `ephemeral` and an all-zero DH output. The delta's
  phrase "small-order seal" reads as the stored side.
- **N3. Response hygiene for export.** The `spa_cors` layer
  (`main.rs:162`) covers the whole router, so registered SPA origins can
  read the export response. Exempt `/account/encapsulation/*` from
  `spa_cors` and send `Cache-Control: no-store`.
- **N4. Exit ordering.** Hosted rows cannot climb today, because Elect
  was dropped at signup. When a later change makes climb reachable, its
  "SHALL NOT export either" plus the destroy step strands data for a
  user who did not export first. Add one sentence saying that export is
  the exit path for the encapsulation key and must come before climb.
  Optionally, climb could refuse while a seal is present and no export
  is logged (B4 makes that checkable).
- **N5. A4 is unreachable for hosted rows.** The user Elect private is
  dropped at signup, so A3 is the only live path. Say so, so nobody
  "fixes" A4 by accepting the operational key.
- **N6. State that the gate is policy, not cryptography.** The operator
  holds the wrap key, so consent is enforced by our code, not by a
  cryptographic guarantee. Say this in the design, the same way the
  responder section does.
- **N7.** Update the `c2_native` doc comment (`privilege.rs`, "We never had
  the user's private key") and the comment in `OperationalEd25519::generate`
  when the code lands.

## What is good

The choice of which private to keep is exact. It is not the operational
X25519 and not Elect. The separate column and envelope, with
cross-rejection, are right, and so is refusing the cookie. The open check
against the current `c2_wrap_recipient` doubles as the C2 rung recheck.
Older rows fail closed with no backfill. Out-of-scope cleanly excludes
PRE, Blob Door, and the recrypt VM. The tasks.md order (schema, seal,
unwrap, consent, export, failure matrix, ADR, `.sqlx`) is buildable.
