## Independent blind take

1. Pin the account/XID as the scope of every listed credential and every revocation target.
2. Pin a device to one credentials row, without inventing a second device registry or physical-device identity.
3. Pin list_devices to non-revoked rows and its existing id, kind, nickname, created_at, and last_used_at projection.
4. Refuse trust, master, or temporary classifications in the device model or list response.
5. Require a clear distinction between authenticating credentials, contact/recovery channels, and the server-held Sign key.
6. Refuse a mailbox or password becoming authority to use or export the Sign key merely because it belongs to the account.
7. Pin revoke_device to the addressed credential on that XID; it must not become account deletion or key destruction.
8. Preserve idempotent revocation, foreign-account/missing-target rejection, and serialization with managed signing already visible in the code.
9. Require claims about revocation to distinguish blocking future credential use from undoing an already-authorized signing operation.
10. Tradeoff: retain the existing device vocabulary for compatibility, while making explicit that a credential row need not identify one physical device.

## Comparison and steelman

The ten lines above were persisted before opening the delta, design, or tasks. The blind product inputs were the proposal's Why, the living device-record requirement, and the cited store methods.

The author answers the core concerns well. The delta keeps email outside credentials, preserves its existing uniqueness rule, separates the managed Sign key and provider material from device rows, and denies A0/A1 direct signing or Elect authority. The existing list projection already excludes key material. The living managed-signing requirement preserves the revocation/signing ordering identified in blind points 8–9; this change need not restate it.

The strongest argument against my initial emphasis on preserving ordinary revocation is that the model also needs to describe account lockout. Counting account login credentials rather than physical devices or signing capability is coherent. An OIDC/password login can preserve account access without acquiring authority to use the managed Sign key. Excluding ssh_git, email, and the key blob from that count is appropriate. I accept that decision and the deliberate separation of this model node from the later management UI and password work.

That separation does not yet pin the enforcement contract. The issues below concern the author's chosen rule, not an alternative device model.

## Owed before acceptance

### 1. Resolve the last-access rule's enforcement and delivery boundary

The delta at `specs/managed-custody/spec.md:59–64,86–90` requires `revoke_device` itself to refuse the final counted credential without confirmation. However, `crates/identikey-keys/src/store.rs:680–706` takes only XID and credential id, and unconditionally soft-revokes a matching row. Its existing test at `store.rs:1485–1511` creates exactly one passkey, revokes it without confirmation, repeats the call successfully, and expects an empty list. The living “Revoke hides the device” scenario likewise has no last-access exception.

The proposal explicitly assigns the confirmation flow to `identikey-core-zlf.6`, while `tasks.md:5` says this node does not edit either store method. Deferring implementation is legitimate. What remains ambiguous is whether the later work changes the shared primitive or adds a guarded account-management operation around it. Those alternatives give the delta's direct-call scenario different meanings. The rule also covers every counted credential kind, whereas the named successor is a passkey management flow.

Reconcile the documents around the intended boundary: name the operation that enforces the policy, identify the downstream owner of enforcement (not just the confirmation surface), explain how the existing primitive/living scenario remain compatible or must change, and record when this future behavior can become living truth. Do not require product implementation in this node. A model-only completion must not imply that today's store already enforces the new rule.

### 2. Pin atomic surviving-access evaluation

The design says revocation sets `revoked_at` under the account lock, but it does not say that counting surviving credentials and deciding whether confirmation is required occur within the same serialization boundary. A caller-side count followed by today's locked revoke can let two concurrent ordinary requests each observe the other credential, then revoke both. The existing lock serializes the writes but does not validate an earlier count.

State that the surviving-access decision and revocation are atomic for the XID, preserving the existing custody-before-credential lock ordering. Add a contract scenario with two live counted credentials and two concurrent unconfirmed revokes: both must not succeed; the request that would remove the final counted credential must leave it active. Assign downstream verification alongside the enforcement owner. This is a contract clarification, not a request to implement or test runtime code here.
