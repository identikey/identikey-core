## Independent blind take

Written from the supplied Why, living passkeys spec, and cited common/login JavaScript before opening the proposal, delta, design, or tasks.

1. Pin distinct, actionable states for unavailable WebAuthn, unfinished prompts, unknown credentials, expired ceremonies, and transport/service failures.
2. Refuse to infer cancellation, account absence, or missing provider software from NotAllowedError or AbortError.
3. Pin unknown-credential guidance to an explicit server result, preserving another-passkey and signup choices without implicit account creation.
4. Preserve fresh challenges, original OIDC context, and pending-signup account reuse on retry.
5. Refuse to interpret platform-authenticator availability or AAGUID metadata as provider installation evidence or an authentication gate.
6. Pin the copied report to an explicit allowlist; arbitrary exception messages, response bodies, URLs, and ceremony/credential/account material must stay out.
7. Separate the shareable report from raw local technical details, retaining programmer diagnostics as text rather than HTML.
8. Require intentional copying, accessible feedback, and an understandable clipboard-failure path with no automatic transmission.
9. Apply the same semantics to login, signup, and device approval without adding credential storage, listing, or revocation behavior.
10. Tradeoff: a small, coarse report offers less debugging detail but a stronger safe-to-share guarantee than heuristic redaction of raw errors.

## Comparison and steelman

The proposal and delta answer the principal blind concerns: unfinished prompts get neutral wording; unknown credentials retain explicit recovery; existing retry and OIDC scenarios survive; provider probing and AAGUID gating are excluded; diagnostics have no credential-management side effects. The design's explicit field allowlist and separation from the technical `<pre>` are appropriate. Keeping unavailable WebAuthn and insecure context in one visible status is consistent with the contract; the report's individual booleans preserve the available facts.

Against my blind take, a manual-copy fallback need not block this bounded change: the proposal explicitly permits clipboard refusal to leave the failure visible. It should still announce copy failure and never claim success, consistent with the inherited accessibility requirement. A compatibility matrix, provider enumeration, and support submission would expand scope without resolving the stated problem.

## Owed before acceptance

**R1 — P2: The report's stage vocabulary omits existing pre-prompt failures.** `design.md:28` restricts the stage to support check, prompt, or server finish, while the delta at `specs/passkeys/spec.md:26` requires a report containing the ceremony stage for a failure status. Signup can fail during initial `POST /signup` or registration renewal before `navigator.credentials.create` (`crates/identikey-server/src/pages-signup.js:15`, `:20`). Device approval can fail during `/device/assert/begin` before `navigator.credentials.get` (`pages-device.js:20`). Login retry can fail while fetching fresh options before opening the prompt (`pages-login.js:39`). All reach the shared failure path. None is a support check, an unfinished browser prompt, or a server finish.

The strongest defense is that these three labels intentionally compress the lifecycle. Coarse stages are reasonable, but naming an options-fetch failure “prompt” or “server finish” would assert an operation that never happened—the same evidentiary problem this change is meant to remove. Amend the stage contract to cover preparation/renewal truthfully, without prescribing a detailed state machine. Also decide how the existing device-denial failure, which calls `showFailure` at `pages-device.js:57`, is represented if it receives the same copy control. Pin the chosen mapping in the design and an acceptance scenario; require pre-prompt failure coverage on all three surfaces. The existing task that checks only presence of the error name and omission of a credential id would not catch a wrong stage.

Two owed checkboxes are appended to `tasks.md` for this single finding. No other issue blocks acceptance.

## Implementation observations

Keep the allowlisted fields typed and bounded: `responseError` currently assigns parsed `data.error` directly to `error.code` (`pages-common.js:65`), so the serializer should not accept an arbitrary object as a server code. Exercise sentinel secrets in raw error descriptions, response extras, and ceremony data to verify that the clipboard payload is built independently from technical details. These observations reinforce the existing sanitization contract rather than adding another product surface.
