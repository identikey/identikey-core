Independent ten-line take, written before opening the current design, tasks, or governance delta; based only on the packet's Why, living guild-keyspaces contract, cited code, and ADR-012:

1. Pin an explicit version boundary: v1 roster-admin authorization and genesis-hash keyspace identity remain unchanged until an upstream protocol defines migration.
2. Pin authorization, settlement/finality, and secret release separately, with a checkable compatibility rule preventing weaker mechanisms from bypassing stronger ones.
3. Pin signed bootstrap to one keyspace history and require the outgoing effective policy to authorize every authority transfer, including the entire incoming policy.
4. Pin a deterministic handoff activation point and behavior for concurrent transitions, replay, unavailable proof, and reverted settlement; refuse arrival-order authority.
5. Pin optional recovery before failure, including its scope and evidence; refuse implicit founder, operator, Registry administrator, or last-signer override.
6. Pin the guild XID's authenticated binding and control continuity across keyspace history; refuse an unqualified replacement of ADR-012's existing identifier contract.
7. Pin separate powers for reading secrets, collective Sign/Auth, XID control, and delegated agency; neither membership nor possession of a PTK may imply the others.
8. Pin Registry instance identity and its trust/finality assumptions independently of service discovery; refuse endpoints or node operators becoming authority by inference.
9. Pin adversarial acceptance cases and upstream-owned wire definitions before runtime work; refuse local op kinds, fields, key algorithms, or treating C2 Sign+Auth as a wrap-target.
10. Tradeoff: freezing at the last agreed state sacrifices availability to preserve authority safety; state exactly which reads, releases, signatures, and identity updates remain possible.

The strongest reading of the proposal answers most of the take. The version cut preserves the v1 baseline and explicitly recognizes stale legacy replicas. The XID-first binding avoids a hash cycle while preserving both identifiers. Outgoing authorization covers the whole replacement, retained founder keys lose current authority, and custody is distinguished from threshold cooperation. Recovery cannot be invented by a disputed branch. Registry pins, mutual compatibility declarations, evidence bounds, and upstream ownership are concrete constraints. These are useful architecture decisions; runtime code, a threshold library, and final wire encodings are appropriately deferred.

Three architecture gaps remain. They concern the claimed guarantees at boundaries between those decisions, rather than a competing design.

1. **R6 — Current authority needs a freshness contract, not just internally consistent evidence.** `design.md:83–104` and the delta at `specs/keyspace-governance/spec.md:185–206` require agreement between document, binding, and checkpoint, but the explicit stale check only rejects a checkpoint older than the supplied document. An eclipsed verifier can receive the old document, old binding, and old checkpoint together after a handoff; all three agree and the removed founder still signs under that old state. The same problem affects release: `design.md:178–194` and the delta at `:245–255` admit a complete local-quorum certificate as final while forbidding a stale reader from releasing for a different successor. A partitioned reader seeing only a second valid certificate cannot discover the first from those inputs.

   Steelman: the text explicitly acknowledges late forks and irreversible release, and mandates current-state verification. That is honest about the consequences once a fork is learned. It does not specify how a new or restarted verifier establishes currentness, or when inability to do so stops a new action. Define the freshness and rollback assumptions required for each admitted settlement/release profile, what evidence establishes current authority, and the unavailable result when it cannot be obtained. If a profile offers only conflict detection after observation, state that weaker guarantee explicitly and reconcile it with the stale-reader prohibition. Previously held plaintext can remain usable as already specified. Add cases for a matching old document/checkpoint after handoff, a verifier restored from an old snapshot, and partitioned releasers that each see a different fully signed successor. These cases must cover new Sign/Auth, identity control, and release, not merely document/checkpoint mismatch.

2. **R7 — Reconcile pre-activation effects with the finality gate and abort semantics.** `design.md:140–156` orders document update and key rotation before settlement evidence, and allows an effect to disclose a key. The delta's “Rotation disclosed, settlement missing” case (`:225–229`) explicitly permits that state. Yet “Finality gates secret release” (`:243–255`) requires final evidence before a new secret is released. The document also does not say whether the pre-activation identity update is staged or is the current document required by the collective-control verifier. Publishing a successor-control document while the predecessor checkpoint remains authoritative can make those two required inputs disagree.

   Steelman: creating an inactive signing key and proving possession need not release an existing PTK or confer current authority, and the proposal correctly refuses to pretend an exposed key can be recalled. Make that distinction part of the contract: define which key material may be distributed during preparation, which release needs settlement, and when each document/key becomes usable. State the coherent document/checkpoint and permitted powers after interruption or abort at each effect boundary. The existing allowance for an unavailable unsafe power is acceptable when its trigger is explicit. Add Registry-backed cases for interruption after document publication, interruption after key distribution but before finality, and abort/resume from both states. Their results must satisfy one consistent release rule and must not enable successor control before activation.

3. **R8 — Pin the settlement rule and evidence domains for a settlement-backend handoff.** `design.md:127–159` says the outgoing policy authorizes the replacement and the successor includes the new settlement descriptor. It does not identify which descriptor finalizes that transition. `design.md:208–222` and the delta at `:275–310` additionally require every evidence blob to use the same pin, while a migration may need evidence about both the old and new Registry. The existing negative migration case covers missing outgoing authorization only. It does not settle the case where authorization is valid, the old Registry is unavailable, and only the new Registry supplies finality.

   Steelman: “effective outgoing policy” can reasonably be read to include its settlement rule, and the no-downgrade rule supports that reading. Make it normative: identify the finality rule for the migration itself, any incoming readiness evidence, and the exact boundary after which successor transitions use the new descriptor. Define how authorized old/new domain references are bound to the same migration without either allowing arbitrary mixed evidence or rejecting a valid migration under the blanket same-pin rule. Add cases for old-only finality, new-only finality, a valid completed migration, and loss/reorg of required old-side evidence before activation. Any exceptional recovery route must already be authorized by the predecessor policy.
