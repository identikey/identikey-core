## Blind take (written before design.md, the delta, and tasks.md)

Sources: the proposal Why and What, the living
`openspec/specs/passkeys/spec.md` lines 13-22,
`crates/identikey-server/src/ceremonies.rs` (`client_public_key` :442,
`passkey_manager_compat` :494-524, begin paths :219, :225, :250, :345),
and `crates/identikey-server/src/pages-common.js:18` `credToJson`. The
packet says `web/pages-common.js`, but the file is under
`crates/identikey-server/src/`.

1. Pin one emission point. Every begin path goes through `client_public_key`, then `passkey_manager_compat`, so the hint insert goes there, after the unconditional `obj.remove("hints")`. That covers registration and the discoverable, allow-list, device, and managed assertions.
2. Pin the rule for both creation and request options. The living text covers creation only and bans hints that prefer "a platform authenticator only". Replace that with a rule about the whole list: absent, or exactly the three values in one fixed order.
3. Pin `authenticatorAttachment` as absent. `residentKey` and UV stay `required`.
4. Pin transports as absent. `credToJson` does not send `getTransports()`, so webauthn-rs stores `transports: None`, and descriptors go out without `transports`, which means any transport, hybrid included. Do not add `getTransports()` in this change. A stored `["internal"]` would hide the phone on known-XID asserts.
5. Pin the test change. `main.rs:3105` asserts `hints.is_null()`; it should assert the exact array. Add an assert-path test as well.
6. Refuse a one-value list, a two-value list, a `hybrid`-first list, and any QR drawn by IdentiKey.
7. Refuse the claim that this "enables" hybrid. With no hints and no attachment, current Chromium and Safari already offer a phone.
8. The author must answer this risk. Chrome picks its first screen from the first hint it recognises. With `client-device` first, it might open the platform sheet straight away and pass over the 1Password or GPM chooser. That is the harm the `passkey_manager_compat` doc comment names.
9. Tradeoff: the nudge is unverified and may change nothing, against a possible regression on the vault path. Absent stays legal, so rolling back is a one-line revert.
10. Owed or stated: either a manual check on Chrome with 1Password and on Safari, or a plain "not verified on hardware".

## Steelman against the take

- *Take 8 shows the order is still harmful.* The living harm was an attachment or a single hint that shuts out the other modalities. With all three values sent, the RP says every modality is acceptable, and `client-device` first roughly matches Chrome's default first screen (local passkeys and GPM, with "use a different device" offered). The 1Password extension intercepts `navigator.credentials` before any browser UI, so hint order cannot hide it. iCloud Keychain on Chrome for macOS is itself a client-device credential. The remaining doubt is about hardware behaviour, and the change already labels that as unverified. Sending this back again would move the goalposts away from the contract I set in the first advise.
- *Take 9 says "omit hints" is safer.* It is neutral, but the steer of 2026-09-26 decided to add the hint. I am not reopening that.
- *Take 7 says the change does nothing.* Possibly. The Why now says only "sheet-order nudge", which is the honest claim.

## Contract accepted

The delta requirement "Registration and assertion use webauthn-rs" as
written at `a6c3a8b`:

- Creation and request options never set `authenticatorAttachment`.
- Hints are absent or exactly `client-device`, `hybrid`, `security-key`, in that order. No one-value or two-value list.
- No caBLE in the server and no QR drawn by the server.
- Registration and every assertion begin path are tested for the exact list and order (task 5).
- The change states that it was not verified on hardware.
