## Blind take (written before design.md / tasks.md)

1. Pin a third consent purpose (`rewrap`), not a reuse of `unwrap`. It needs a new migration widening `encapsulation_purpose_known` (never an edit to 0007) and a wrap-digest rule for it.
2. Pin the transcript: the owner's proof must cover source-wrap digest **and** the 32-byte recipient public (and the friend XID if named). `encapsulation_transcript` appends the digest only when `purpose == "unwrap"`; a new purpose that forgets this silently drops the binding. New golden vector.
3. Pin recipient resolution: server resolves the friend's X25519 from the friend's *stored* document at begin, binds it, and rechecks it at finish under lock. A client-supplied 32 bytes the owner never saw is a substitution hole.
4. Pin output: the data key never leaves the process; the result is a §7 wrap (ciphertext); same transaction marks used, writes consent-log `encapsulation_rewrap` with source digest, recipient, output digest.
5. Refuse: a standing/batch grant (one consent → many wraps or recipients), account-cookie-only authority, any new proxy-recryption scheme, wrap targets that are Sign+Auth / `managed_key_blob` / passkeys / small-order points.
6. Refuse the claim that a share is revocable. Once wrapped, the friend holds the data key; revoke = new data key.
7. Disclose: if the friend is C2 with a held seal, IdentiKey can open the friend's copy too; if the friend's seal is null (pre-fcdb920) the share is inert.
8. Pin the identity surface: "friend who logs in with IdentiKey" — RPs see pairwise `sub`, which is not a XID. Naming the friend needs the public XID (base58btc), not an RP sub.
9. Pin HTTP posture if a route ships: `no-store`, no SPA ACAO, no hosted unwrap route regression.
10. Tradeoff: IdentiKey sees the plaintext data key at re-wrap time (custodial) vs. PRE where it never would — accepted for no new crypto and immediate shipping; the exit test still holds because the owner can export the scalar and the friend's wrap is to the friend's own key.

The steer decision (custodial re-wrap, not Umbral or AFGH) is consistent
with the Why. BN254/secp256k1 PRE cannot target a native X25519 public,
and the seal already makes IdentiKey able to open a wrap to the owner
(LEARNINGS 2026-10-21). So rewrap adds no new custodial capability over
the folded `unwrap`. It adds one new *output*: a ciphertext to a named
third party. The contract is narrow and well-bound.

## Notes for act (non-blocking; implementer should take them)

**A. New migration, not an edit to 0007.** `encapsulation_purpose_known`
and `encapsulation_wrap_digest` are in `0007_encapsulation_key.sql`. Widen
them in a new migration (drop and re-add the constraints) and add a CHECK
so `friend_xid` and `recipient` (32 bytes) are non-null iff
`purpose = 'rewrap'`. Editing 0007 breaks the sqlx checksum on any database
that already ran it. `consent_log.action` has no CHECK, so
`encapsulation_rewrap` needs no schema change there.

**B. Audit should name the key, not only the person.** The delta logs
audience = friend XID and purpose = source-wrap digest hex. After the
friend rotates, neither tells you which X25519 received the data key. A3
`proof_bytes` is a WebAuthn assertion over a random challenge, so it does
not carry the recipient either. Keep the `encapsulation_attempts` row
(with `recipient`) and do not garbage-collect it, or put the recipient into
the custody event. Recording the SHA-256 of the output wrap would also help.
Neither change touches the pinned transcript.

**C. Say the two things a user will ask.** (i) A friend wrap cannot be
revoked. Once returned, the friend holds the data key, and revocation
means a new data key. (ii) If the friend is a C2 row with a held seal,
IdentiKey can open the friend's copy too, under the friend's
`encapsulation_unwrap`/`rewrap` consent. If the friend's seal is null
(pre-`fcdb920` signup), the friend cannot open the wrap through IdentiKey.
They need an exported scalar or a wallet, and a pre-seal C2 row has
neither, so the wrap stays inert. That second case is a real UX dead-end
for the recording share. Begin succeeds, because `c2_wrap_recipient`
exists, and the friend can still never read the recording. Consider
having begin report `has_encapsulation_key` for the friend in the begin
response (not a refusal). Or record it as a known limit in the ADR-012
amendment.

**D. Friend reload: no `FOR UPDATE` on the friend's custody row.** Finish
already locks the attempt row, the owner's credential row, and the owner's
custody row. If it also locks the friend's custody row, two owners
rewrapping to each other take locks in opposite order and deadlock.
Postgres aborts one, which fails closed but is noisy. A plain read is
enough. Rotation is the only race. Its worst case is a wrap to the
friend's just-retired key, and the friend's seal for that key was nulled
by the rotation, so the wrap is inert. If you want a lock, use `FOR SHARE`
in XID byte order.

**E. Unused row after a rotated-friend refusal.** This matches the
existing rollback pattern, since `WrongWrap` also leaves the row unused.
The row cannot succeed later, because the stored recipient will not recur,
and the 5-minute TTL bounds it. Fine as written.

**F. Tests.** Task 8 omits two begin refusals that the delta requires:
friend XID equal to the owner, and friend with no stored document (or a C1
friend). Add them to the same test set.

**G. Fold.** `guild-keyspaces` still says a held C2 PTK opens "under the
managed-custody consent for `encapsulation_unwrap`". After fold, rewrap is
a second path, and it puts a house PTK in the hands of a non-roster reader
with no keyspace op. A member can already leak a PTK, so this grants no
new capability. Still, the folder should add one sentence there (or in the
ADR-012 amendment) so that line does not read as exhaustive.

## Verdict

Accept. The contract binds purpose, source wrap, and recipient. It resolves
the recipient server-side and rechecks it before open. It keeps the data
key and the scalar off the wire, and it invents no cryptography. Notes A–G
are things to do during act, not reasons to re-prepare.
