Reviewed the current working-tree contract for node `identikey-core-max.2`, including the ACTIVE BUILD proposal and 2026-10-30 steering. This is a design review, not an implementation verdict. The library scope and the decision to ship email and SMS together are accepted. Four security contracts need to be pinned before implementation; owed boxes are appended to `tasks.md`.

## Blind pass

The following take was persisted in `2026-11-02-blind-take.md` before opening the delta, design, or tasks. Inputs were only the proposal's Why, the living account-recovery spec, and the cited recovery marker/proof code.

1. Pin the library boundary: hosted email recovery already exists; this node must make the library's currently unchecked proof meaningful.
2. Pin account identity and allowed recovery purpose to each issued factor, verified proof, and resulting managed access.
3. Pin C1/C2 eligibility and refuse any path from an A1 proof to key recovery, raw keys, Elect keys, or challenge signing.
4. Refuse publicly forgeable success proofs, including keeping `AccountRecoveryProof::granted()` as a production bypass.
5. Pin email and SMS as supported library channels, with delivery separated from verification and no requirement to replace the hosted journey.
6. Pin the authority that chooses a recovery destination: possession of an arbitrary caller-supplied address must not recover someone else's account.
7. Pin expiration, cryptographic unpredictability, bounded guesses, and atomic single use, including concurrent redemption and failed attempts.
8. Pin persistence and clock responsibilities so restart, multiple workers, and caller-controlled timestamps cannot silently weaken verification.
9. Preserve hosted email uniqueness, same-XID replacement passkeys, and the prohibition on signing from a recovery session; integration scope must be explicit.
10. Tradeoff: a small synchronous store/delivery abstraction is reasonable, provided security-critical atomicity and caller trust obligations are testable contracts.

## Comparison and steelman

The author answers much of this take. `design.md:5-12` places the ceremony in `identikey-recovery`, keeps routes and carrier clients out, and assigns clock, directory, and persistence to caller ports. Returning a secret to a trusted delivery caller is appropriate here. I do not require a transport trait, a database adapter, synchronous APIs, or a particular TTL.

`design.md:26-28,44-49,58-64` rejects unbound destinations and C3/C4, rechecks custody, removes the public unchecked constructor, separates bootstrap from recover, and preserves the key-recovery type boundary. Those are substantive safeguards. A proof need not embed a stale custody rung when the directory supplies current eligibility. Unlimited failed email presentations are also reasonable with an unpredictable 32-byte secret; the SMS budget need not be imposed on email.

The strongest case for acceptance is that single use, five attempts, and XID binding already express the intended outcomes and implementation could choose safe ports. The remaining problem is that these are security properties of the public port and proof contracts, not merely algorithm choices. Sequential in-memory tests can satisfy the listed scenarios while leaving the races and authorization ambiguities below unresolved.

The existing hosted behavior is real: `crates/identikey-server/src/email_link.rs:37-49` returns a redeem URL and redeems it; `crates/identikey-keys/src/store.rs:246-280` atomically consumes the token and writes the bound account's email. Its concurrent redemption test at `store.rs:1499-1522` already requires exactly one winner. This review does not request replacing that flow or adding another hosted token store.

## Owed contracts

### R1 — High: define an atomic factor-store transition

Evidence: `design.md:10-12,34-43`; delta `specs/account-recovery/spec.md:27-31,47-69`.

“Consume before returning” does not specify whether competing finishes can both read a live factor and both return proofs after unconditional writes. Separately updating SMS attempts permits lost increments; a successful finish racing the fifth failure needs a defined ordering. The store interface is the place that must guarantee these outcomes across all users of a store, even if the first adapter is in-memory.

Owed: specify a linearizable conditional transition covering live state, expiry, attempt budget, and consumption, or an equivalent serialized transaction contract. Only a successful committed consumption may issue a proof; store failures must not issue one. Define the fifth-failure/success race and failed-attempt persistence. Add adapter-contract tests for two matching finishes, concurrent wrong attempts, the final-attempt race, and persistence errors. No production database adapter is required for this node.

### R2 — High: make destination and account binding an explicit API contract

Evidence: `design.md:16-30,36-37,58-61`; delta `specs/account-recovery/spec.md:73-79`.

The design sensibly says the directory binds destination to XID at begin, but the delta does not require that lookup or reject a supplied XID mismatch. “Whose XID is the proof's XID” does not identify an independent enrollment target or how the closure receives the authorized XID. A closure can capture another account while the library checks only the proof account. The bootstrap proof is only required to retain purpose, leaving unspecified whether it proves a particular email/phone or merely possession of some channel.

Owed: define the trusted directory result, the immutable factor binding (channel, destination, purpose, and recover XID), and how acceptance passes or validates the authorized target. State what happens if the destination is unbound or rebound between begin, finish, and acceptance. For bootstrap, either preserve verified-destination provenance for the create callback or explicitly limit the proof to channel possession and prohibit treating an independently supplied address as verified. State that callbacks are trusted integration code and must use the authorized inputs. Add mismatch, binding-change, and cross-channel/target substitution cases. This does not require storing hosted SMS addresses in this node.

### R3 — High: settle proof lifetime and the alternate access path

Evidence: `crates/identikey-recovery/src/lib.rs:76-102`; `design.md:53-65`; delta `specs/account-recovery/spec.md:81-114`.

The existing proof is `Clone + Copy`, and `restore_access` unconditionally turns any proof into `ManagedAccess`. The new design adds consuming a factor but does not say whether the resulting proof remains copyable or reusable. “The closure runs once” could mean once per invocation, allowing one factor to authorize arbitrarily many invocations. The delta also explicitly keeps `restore_access(AccountRecoveryProof)` without stating whether a bootstrap proof or a recover proof for an account now at C3/C4 can produce an authorization-bearing result through that path.

Owed: define whether proof acceptance is single use, its validity after finish, and the behavior when the callback fails. If single use is intended, remove ordinary duplication/forging paths and consume the proof at acceptance; if reuse is intended, state its bounded authority explicitly. Reconcile `restore_access` with purpose, identity, and current custody checks, or explicitly make its result non-authorizing and prevent it from bypassing the acceptance functions. Align the delta/tasks with the design's removal of public `granted()`. Add compile-fail or behavioral checks for bypass construction, duplicate acceptance, bootstrap-to-managed-access, and custody changes after finish. No particular session mechanism is prescribed.

### R4 — Medium: require unpredictable generation, not just output shape

Evidence: `design.md:19-24`; delta `specs/account-recovery/spec.md:5-23`.

The design says email bytes are random, but neither the delta nor the SMS definition requires a cryptographically secure source. A fixed six-digit string satisfies the present SMS shape/hash scenarios. Challenge-id generation, uniqueness, and insertion-collision behavior are also unspecified; reusing an identifier must not replace a live factor or reset its guess budget.

Owed: require cryptographically secure email/SMS generation, unbiased six-digit sampling including leading zeros, and a challenge-id collision policy that cannot overwrite live state. Define fail-closed behavior on entropy or insertion failure and unambiguous hash input encoding. Add focused generation/error/collision coverage without relying on statistical tests to establish cryptographic security.

## Nonblocking clarifications and limits

The Why's claim that there is no in-repo way back is stale against the living spec. Reword it around the missing library ceremony when amending the proposal; it is not a reason to expand implementation scope.

The steered SHA-256(challenge id || secret) scheme is preserved. For six-digit SMS, a reader of the stored challenge id and digest can enumerate the code space offline; hashing alone is not protection against that reader. Document the trusted-store boundary and later route ownership of begin/resend abuse limits. These observations do not demand a transport implementation or unilaterally replace the recorded hashing decision.

Likewise, arbitrary caller closures cannot be sandboxed by a Rust proof wrapper. “No key bytes” should describe the library's proof/output API and the trusted caller's obligations. Existing `create_managed` accepts a managed blob and returns an XID (`store.rs:284-330`), so later wiring can capture its inputs without adding key material to the recovery proof.

Validation is document and source inspection plus the packet's review-file acceptance command. Product tests were not run because no implementation was changed. No product code, living spec, banner, or fold was changed. Re-review the reconciled design, delta, and tasks after R1–R4 are addressed.
