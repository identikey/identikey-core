## Blind pass

The following take was persisted in [2026-10-31-blind-take.md](2026-10-31-blind-take.md) before opening the delta, design, or tasks. Its evidence was the proposal's Why, the living managed-custody requirements, and Papyrus `src-tauri/src/commands/identity.rs`.

1. Pin Papyrus as the first native client, with an explicit boundary between local identity creation and enrollment into an OP account.
2. Pin the OP device record to an ordinary `credentials` row with a supported login kind, rather than introduce a separate device authority.
3. Require authenticated account authorization and fresh possession of the exact native public key before attaching that key to the account.
4. Bind enrollment proof to the intended account, OP, operation, key, and expiring single-use attempt so it cannot be substituted or replayed.
5. Refuse to treat Papyrus `device_enroll` as remote enrollment: it currently returns local identity metadata without contacting the OP.
6. Refuse to infer hardware protection from the `enclave` feature; `device_signer` may return Secure Enclave, TPM, or persisted software.
7. Require explicit software-fallback behavior and honest backend labels; a reported backend alone must not become trusted hardware attestation.
8. Pin how the new credential actually authenticates an account, so its inclusion in surviving-access counts cannot conceal an unusable login.
9. Preserve unconditional `revoke_device`, use the shared account-access revocation policy for account UI, and make revoked native keys fail authentication.
10. Accept a narrow Papyrus-first integration as a tradeoff against multi-client scope, provided retry, cancellation, duplicate enrollment, and authority boundaries are specified.

## Comparison and steelman

The proposal deliberately limits this node to choosing and recording the journey. `proposal.md:53` onward excludes account-binding implementation and protocol beads; `tasks.md:3` records the client decision. That is a legitimate scope. My blind take's transcript, retry, cancellation, duplicate, and native-login concerns belong to preparation of the later account-binding work, not a demand to expand this node into that implementation.

The delta answers the key local/remote distinction correctly: Papyrus `device_enroll` only obtains the signer and returns identity metadata (`identity.rs:139–141`). The `identikey_auth` row, signed device proof, no new Elect, and independent hosted passkey path are appropriate architectural boundaries. The schema already has a `device_public_key` field for this credential kind (`crates/identikey-keys/migrations/0001_initial.sql:83–110`).

The delta also correctly allows software and rejects the feature flag as hardware evidence. In the actual code, hardware initialization errors fall through to software even when the feature is enabled (`identity.rs:77–100`). Read `design.md:15–18` as backend preference, not a hardware guarantee. Describing it explicitly as “attempt hardware, then software on failure” would improve accuracy, but the delta already permits that behavior and this is not a separate blocker.

## Owed contract corrections

### R1 — Distinguish account-access revocation from the primitive

`design.md:11` says “Revoke is `revoke_device`”; the proposal gives the same journey-level direction. The delta at lines 14–15 and its scenario at lines 44–48 mention only that primitive. Taken strictly as a primitive assertion, the scenario is correct and should remain: `revoke_device` must still revoke even the sole credential.

However, the living **Surviving access is an account login** requirement (`openspec/specs/managed-custody/spec.md:841–874`) requires later account-access callers to use the shared kind-generic operation. That operation now exists at `crates/identikey-keys/src/store.rs:889`, counts `identikey_auth`, and returns `LastAccessConfirmationRequired` when appropriate. Calling the primitive directly for the native account journey would bypass that decision and remove the last login without confirmation.

Clarify the proposal, design, and delta: the primitive remains unconditional; user-facing account-access revocation of a Papyrus credential must use `revoke_account_access` and its existing confirmation policy. Add a native-credential scenario where the last login remains active without explicit confirmation. This inherits an existing policy and requires no new revocation implementation in this node.

### R2 — Carry the deferred delivery boundary into the delta

The proposal and tasks explicitly defer the account-binding route, but the delta's account-enrollment SHALLs and scenario (`specs/managed-custody/spec.md:10–17,31–42`) do not carry that qualification. The sole completed task chooses Papyrus. Once the delta is folded into living truth, its wording would lose the distinction between the chosen future account contract and behavior delivered by this node.

The strongest defense is that these are intended interface constraints for a later node, and I accept that intention. Make it explicit in the delta itself, as the living surviving-access requirement does for its deferred operation: this node selects Papyrus and documents local behavior; it does not deliver OP account binding or native account login, and folding this decision must not claim those are available. Keep the future row and proof constraints, labeled as such. State that later work must establish usable native account authentication before relying on those rows as surviving access. Do not create protocol beads or prescribe wire formats here.
