Inputs were the packet's Why, the three living specs, cited code, and the named learning. These are concerns the author must answer, not a competing design.

1. Pin this node to C2 operational Sign+Auth; any C1 authorization policy needs its own explicit contract.
2. Pin Ed25519 private/public correspondence across persisted material, the C2 document, and the identikey-auth software signer; refuse Schnorr protocol expansion.
3. Preserve the user's Elect/Transfer privileges and X25519 wrap target; changing our operational key must not silently reassign management authority.
4. Accept only bounded, canonical v1 Challenge bytes and bind authorization to their exact digest; refuse arbitrary signing payloads or public blob access.
5. A fresh account-bound A3 assertion or genuinely user-held A4 proof must authorize this instruction; a cookie or our own Sign key cannot supply consent.
6. Bind the ceremony to the initiating client, challenge, account, expiration, and one-time use so swapped inputs, stolen identifiers, and retries cannot redirect a Response.
7. Serialize key use against custody exit, document changes, and credential revocation; a previously approved instruction must not outlive the authority it relied on.
8. Persist authorization before private-key use and completion/failure afterward, with explicit fail-closed and crash/retry semantics that never release an unaudited Response.
9. Keep verifier duties at the edge while enforcing local challenge validity and user-visible intent; test the real signup blob through an independent verifier.
10. Tradeoff: reminting legacy Schnorr identities avoids migration ambiguity but changes identity; make rejection explicit and keep Elect export and existing OIDC behavior outside this slice.

## Comparison and steelman

The revision resolves substantial concerns. Decision 2 correctly places algorithm checks on the operational key, requires exact-byte roundtripping, caps input and nonce sizes, states time limits, and rechecks expiry. Decisions 1 and 8 retain Elect/X25519, select Ed25519, bind an encrypted seed to account/public key, check the derived public, reject legacy blobs, and name the seed/adapter seam. C2-only scope is explicit. Decision 5 makes the account, challenge, request id, and retrieval commitment immutable. Decision 7 defines both exit orderings and permits retrieval of a response completed before exit. Those are useful contracts, not merely renamed tasks.

The strongest case for acceptance is that local, deterministic Ed25519 signing and Postgres transactions make a compact implementation possible. Native clients need only a small ceremony; this node need not reproduce edge nonce consumption, identity resolution, or capability issuance. I agree. I also withdraw any implication in my blind take that arbitrary external audiences must be authenticated by core: local admission plus accurate consent presentation is enough for this claimant. Exact database layouts, handler names, and a broad key-management platform need not be designed here.

However, the following three gaps still change observable authorization or retry behavior. They cannot be settled by choosing ordinary implementation details. R1 from the first review is addressed; R2–R4 are only partly addressed. R5's architectural direction is answered, but its promised restart and malformed/swapped-envelope acceptance cases are still absent.

## Required revisions

### R6 — Resolve the indistinguishable crash outcomes

**Evidence:** design.md:75–81, combined with the durable-before-use requirement at delta:40–43.

Consider two executions: (a) commit authorization, crash before signing; (b) commit authorization, sign, crash before persisting the Response/completion. Under the described state model both restart with the same authorization row and no completion. Calling that row `authorized-unused` cannot establish that the private key was unused. Allowing finish to sign again satisfies (a), but violates the explicit “do not sign again” rule in (b). Withholding the Response when logging fails is correct but does not preserve it across process loss.

Specify the durable states, the atomic claim, and the recovery rule for an attempt whose key-use outcome is unknown. A conservative terminal/indeterminate attempt is acceptable; so is an explicitly revised policy permitting deterministic recomputation with precise audit semantics. Do not promise both recovery of every authorized attempt and at-most-once software key use without accounting for this boundary. State where a completed Response is durably stored and whether its persistence and completion audit commit atomically. State what retrieve returns while unresolved and after restart; it must not silently initiate another signing attempt.

Also identify the persisted, integrity-bound association between request id, exact challenge digest, authorization, and terminal outcome. Current `ConsentAppend` (`store.rs:120`) and `ConsentHashInput` (`consent.rs`) do not have request-id/digest fields; a concrete versioned record or binding is needed, not necessarily new columns.

**Acceptance:** crash immediately before key use; crash immediately after signature generation but before result persistence; completion-log failure followed by restart; concurrent finish; retry/retrieve in every resulting state. Each case must state whether another key use is allowed and which audit/result survives. Include definite pre-sign failures separately from unknown outcomes.

### R7 — Specify what proves account-bound consent

**Evidence:** design.md:63–71. “A4 … from a user key, not the managed operational key” excludes one invalid key but does not establish which keys may authorize this account.

Pin the authoritative account-to-access-key association and eligibility/revocation checks for A4. A valid Response from an unrelated attacker's key must fail even though that key is user-held and differs from the managed operational public. Do not equate algorithm, caller-supplied XID, or an `A4` label with account authority. Existing hosted signup drops the user's Schnorr Elect private, so that key is neither an available nor protocol-compatible implicit A4 credential.

Specify the consent transcript's version/domain, unambiguous encoding, digest, and freshness limit. For A4, define the separate consent Challenge and how it commits to the immutable edge Challenge/account/request/client fields: the pinned protocol signs a structured Challenge with `v, aud, nonce, iat, exp`, not an arbitrary digest. An ordinary user Response to the edge Challenge alone does not bind request id or retrieval commitment. This is verification of core's own consent ceremony, not promotion of core to edge verifier.

For A3, name the supported way that the same immutable instruction becomes bound to the assertion. Existing `CeremonyHub::begin_assert` uses library-generated WebAuthn challenges and `finish_assert` returns XID/pending authorization; neither currently binds this instruction. A server-side immutable association can be valid if specified; changing only the browser's challenge cannot match the stored verifier state. Define the client-visible begin/consent/finish/retrieve inputs and outputs and choose supported retrieval proof variants. Decision 5 currently allows a holder public at begin but only describes a verifier at retrieve; holder-key possession needs its own defined proof if retained.

**Acceptance:** unrelated valid A4 signer; managed-key A4 signer; wrong account; swapped client commitment; wrong ceremony; expired consent with a still-live edge Challenge; and a successful supported A3/A4 path including retrieval. Unsupported proof variants must fail closed rather than inherit a generic login result.

### R8 — Extend serialization to access-credential revocation

**Evidence:** design.md:68–69 and 85–90; `store.rs:503–516` (`revoke_device`) versus `store.rs:677` (`apply_document_update_tx`).

The shared custody-row lock usefully serializes exit and document changes. It does not serialize credential revocation: `revoke_device` updates `credentials` without acquiring the custody lock. A finish can check an active credential, then revocation can commit, then finish can decrypt/sign. Both operations obey the present revised design.

Define the ordering point for credential authorization versus signing, and a compatible locking/fencing rule covering credential revocation as well as document/key changes. Clarify the transaction boundaries: committing the pre-use authorization releases ordinary transaction row locks, so custody/key/credential authority must still be protected and rechecked for the subsequent key-use phase. No particular lock order or schema is mandated, but “checks revocation” alone is insufficient.

**Acceptance:** credential revocation wins and prevents key use; signing wins before revocation under the declared ordering; operational-key removal wins; signing wins before exit and the completed result remains retrievable. Add these to the delta with expected outcomes. The current delta includes only the exit-wins case despite the checked R4 task promising both orderings.
