## Verdict

Send back. The property (“Basic OP and Config OP are green against
127.0.0.1”) is the right *kind* of instrument, but the plan as
written cannot become green against the OP we actually have, and
the red-job rule now fights the living CI.

## Steelman against

“Wire the suite, fail the build on red, leave it red until the OP
is right. That *is* the instrument. Do not `continue-on-error`.”

That was coherent when the code flow did not exist. The flow
landed and folded (`openspec/specs/oidc-provider/spec.md`). A
required job that stays red is no longer a property-red — it is
main painted red for work this change lists as out of scope.

## One real tradeoff

**Config OP only** (discovery document; can go green on today’s
OP) versus **Basic OP** (the real referee for the code flow).
Basic OP, as OIDF defines certification, requires confidential
clients. We advertise only `none`. Pick one: shrink the
instrument to Config OP, or open a change for
`client_secret_basic` / `client_secret_post` and two extra
clients *before* this job is allowed to fail the build.

## Findings

1. **Basic OP needs secrets we refuse to have.**
   OIDF’s OP testing instructions: without DCR, register three
   clients — two `client_secret_basic`, one `client_secret_post`
   (https://openid.net/certification/connect_op_testing/).
   Discovery advertises only `token_endpoint_auth_methods_supported:
   ["none"]` (`crates/identikey-oidc/src/discovery.rs:40`).
   `Client` has id, sector, redirects — no secret
   (`crates/identikey-oidc/src/subject.rs:22-27`). This change’s
   out-of-scope line is “implementing endpoints,” already folded.
   It does not add confidential-client auth. A required Basic OP
   job will fail `main` forever for a missing grant this node
   must not implement.

2. **Login is unspecified.**
   Design: boot with `IDENTIKEY_DEV_LOGIN=1` and a pre-seeded C2
   user. The suite is a confidential/public *client*; it does not
   paste a 64-hex XID into an HTML form. The only login path is
   `GET|POST /authorize/dev` (`crates/identikey-server/src/main.rs:66-71`).
   No Selenium script, no `user-complete` URL, no `login_hint`
   contract. Act would invent one.

3. **Red-job rule contradicts itself now.**
   `design.md`: “A red job is success of the instrument until the
   code flow lands; do not `continue-on-error`.”
   `specs/oidc-provider/spec.md`: “A failing plan SHALL fail the
   build.” Code flow has landed. Implementing the SHALL as a
   required GitHub job fails every push. That is not property-red;
   it is a broken gate.

4. **No seed, no image, no network.**
   Design says pin a digest if a prebuilt image exists — it does
   not name the image or a digest. No fixture or CLI for the
   “pre-seeded C2 user” (`create_managed` needs a real XID
   document). No word on how the suite container reaches
   `127.0.0.1:8080`, or that local-suite redirect URIs are the
   suite’s callback (typically TLS on 8443), not
   `IDENTIKEY_CLIENT_REDIRECT=http://127.0.0.1:9999/cb`.

5. **Plan identifiers are missing.**
   “OIDC Basic OP” / “OIDC Config OP” are certification *profiles*,
   not `run-test-plan.py` arguments. Act needs the exact plan
   names (commonly `oidcc-basic-certification-test-plan` and
   `oidcc-config-certification-test-plan`) and a sample config
   JSON. Licence research is done and solid (`docs/LEARNINGS.md`
   2026-08-18; MIT runner, not a Cargo dep).

## What is solid

- Instrument, not a Cargo crate. Matches LEARNINGS and
  `deny.toml` private-crate scoping.
- Config OP against
  `/.well-known/openid-configuration` is the right first referee
  for “did we advertise code and S256.”
- Official certification / the mark stays out of scope.
- Existing `rust.yml` is the right place to add a job; it already
  has Postgres 17.
