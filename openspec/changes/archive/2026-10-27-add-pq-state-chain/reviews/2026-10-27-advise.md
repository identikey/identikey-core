## Answer

The construction can preserve an existing XID and bind its control to a PQ key without an IdentiKey-held pin. Its bootstrap trust is a **verifier-retained, previously authenticated migration checkpoint**. It does not remove the need for retained trust state: a verifier with no such checkpoint must refuse classical migration after classical authorization leaves policy. That limitation is correctly stated, and is not itself a reason to send back.

The successor rule is also sound in intent: authorization comes from the previous PQ control key, with possession of any replacement key. However, the contract is not ready to implement because it leaves genesis re-entry and competing valid successors ambiguous, and its promised resolver delivery has no defined representation. These are bounded contract gaps, not a request to replace the design or solve global freshness.

## Blind independent take

Written to `reviews/2026-10-27-blind-take.md` before opening `design.md` or `tasks.md`, using proposal Why/What, the requested living requirements, cited verification code, and ADR-001/007/008. Preserved verbatim:

1. Pin the original inception-key-derived XID throughout migration and rotation; neither a PQ key fingerprint nor a server account mapping may replace it.
2. Pin canonical, domain-separated record bytes binding XID, sequence, predecessor, control authority, and operational authority together.
3. Require the existing current Elect authority to authorize migration while classical authorization remains trusted, with possession of the proposed PQ control key.
4. After classical authorization leaves policy, refuse first-contact migration without a previously authenticated checkpoint; new PQ possession cannot authenticate the old XID by itself.
5. A retained checkpoint must belong to the verifier’s trust state and be usable away from IdentiKey; a server-served digest cannot establish its own authenticity.
6. Require prior PQ control authority for every successor and new-key possession for replacement; classical operational keys must never reset the chain or its control policy.
7. Distinguish authenticated chain ancestry from freshness: reject rollback and observed forks, and preserve consequential-resolution requirements without treating a sequence as proof of latestness.
8. Preserve the existing URN grant and subject seam: verify.rs returns a classical fingerprint, so this state alone cannot make today’s response authenticate the PQ-bound XID.
9. Keep Sign/Auth separate from Elect-like control, and do not quietly enable successor pre-commitment without ADR-008’s custody separation and recovery conditions.
10. Tradeoff: portable verifier checkpoints and fail-closed cold starts sacrifice immediate onboarding and recovery availability to avoid silently granting post-cutoff control to classical forgeries.

## Comparison and steelman

- **Stable identity and authority separation are answered.** `design.md:5–7,21–25` keeps the XID fixed, commits operational authority separately, and checks successors against the previous head. That matches ADR-001 and ADR-008. Optional pre-rotation is not a substitute for PQ control authorization; this change does not need guardian recovery or successor precommitment to establish its narrower guarantee.
- **Post-cutoff bootstrap is answered in principle.** `design.md:15` and the delta at `specs/pq-state-chain/spec.md:19–33` reject an unanchored classical migration even when an attacker supplies a valid PQ countersignature. A cold verifier cannot learn historical legitimacy from that pair after cutoff. Calling the retained digest a pin does not make it a server-held authority: the verifier can own it independently. The contract should explicitly preserve that ownership at the API boundary, as part of R1 below.
- **Freshness is honestly limited.** `design.md:27–29` correctly declines to prove that no later record exists. I withdraw any implication in the blind take that this node must add a resolver or a new freshness oracle. Detecting two supplied, valid branches is a separate obligation, addressed by R2.
- **Authentication scope is correct.** In sibling `identikey-protocol/crates/identikey-auth/src/verify.rs:57–73,79–82`, the PQ signature verifies under the supplied PQ public key while the returned fingerprint remains classical. `design.md:31–33` does not claim to fix that binding here. Keeping the URN grant and `subject()` seam unchanged agrees with `openspec/specs/oidc-provider/spec.md:242–261`; the later session-proof node remains necessary.
- **The strongest favorable reading** is a small caller-owned verification state machine, with the existing resolver supplying only bytes and the caller already enforcing ancestry and duplicity. That would satisfy much of this review. Those caller obligations and the supplied-byte format are not currently specified, so an implementer cannot distinguish that reading from an unsafe or incompatible one.

## Owed before acceptance

### R1 — High: make bootstrap one-time and distinguish an anchor from the current head

The migration rule (`specs/pq-state-chain/spec.md:21–33`) accepts a signature pair while classical signatures are trusted, or an already-retained digest after cutoff. The rotation rule (`:47–59`) applies only to records after the first. Neither defines what processing a first record does when that XID already has a PQ head.

Concrete cases: after accepting checkpoint G and successor H, replay G; or, while classical authorization is still enabled, submit a different sequence-1 record G2 signed by the classical Elect key and an attacker-owned PQ key. G2 satisfies the stated migration admission rule but has no authorization from H's control key. Replaying G after cutoff likewise satisfies the retained-digest predicate. These must not become alternate routes for replacing or rewinding H. The favorable interpretation is that “first” means only the initial bootstrap of an uninitialized verifier; make that an explicit state-machine rule.

Specify trusted verifier input/state keyed by XID, retained migration anchor versus latest accepted head, and one-time initialization. Revalidation of an old anchor may succeed as historical verification but must not move the head. A different genesis must not replace an established chain. Untrusted resolver bytes or a server-provided digest must not populate the trusted checkpoint input. Loss of verifier trust state after cutoff must remain fail-closed. Add negative cases for these paths, including replay after a valid PQ rotation.

### R2 — High: define the result for two valid successors of one head

`specs/pq-state-chain/spec.md:47–53` makes a valid successor the head, but specifies no duplicity result. Given H and two different successors A and B, both signed by H's control key with the same `prev` and `seq`, processing A first can promote A and then dismiss B as a previous-digest mismatch. Processing B first can select B. Both branches were authorized relative to H; a mismatch against the newly selected head is not evidence that the other branch was invalid.

The living resolution contract (`openspec/specs/xid-resolution/spec.md:7–29`) explicitly refuses a winner when valid documents diverge. Its `bc-xid` provenance comparison does not automatically compare the new PQ hash chain. Specify which layer detects PQ-chain duplicity and prevents a successful authority result once both valid branches are supplied, including the case where one was already accepted. Cover both input orders, repeated identical records, and an invalid competing signature that must not count as a valid fork. No claim to detect an unseen or withheld branch is needed.

### R3 — Medium: reconcile the promised resolver surface with the actual byte contract

`proposal.md:25` says the record is reached through the existing XID resolution surface. The living requirement (`openspec/specs/xid-resolution/spec.md:55–69`) requires that surface to return the stored XID document bytes, not a PQ state record or chain bundle. `design.md:3–9` defines a standalone map, and the three existing tasks cover encoding and verification only. No assertion, locator, bundle representation, or caller-supplied chain interface connects those contracts.

Define the minimal delivery contract: where the PQ record/chain lives relative to the XID document, how a cited digest and required predecessors are obtained, and how digest verification and established PQ authority survive an independently changed classical document. Preserve the well-known response body and existing resolution-tier behavior. Alternatively, explicitly narrow this node to a protocol codec/verifier that accepts caller-supplied records and move the claimed resolver journey to named follow-up work. This does not require adding a new resolver in this node.

## Encoding note

The delta requires a versioned record (`specs/pq-state-chain/spec.md:5`), but the field list (`design.md:7`) omits a version, and signatures cover raw unsigned bytes without a stated protocol context. Before freezing vectors, specify the version and signing context, canonical field/key encodings, and enforce the stated v1 profile of exactly one ML-DSA-65 control key with threshold 1. Unknown versions, zero thresholds, and other control profiles must not silently become alternate v1 interpretations. This is implementation-contract detail to settle alongside the existing encoding task, not a demand for a new cryptographic primitive.

## Validation and disposition

This is a document and cited-code review; no product code was changed and no runtime tests were run. The blind pass preceded design/task inspection. Owed checkboxes R1–R3 were appended to `tasks.md`; the existing work and banner were preserved. Re-review the amended contract before act. This review does not authorize implementation or folding.
