## Blind take (written before opening design/tasks/steer/specs/reviews)

Sources: Why, living `managed-custody` "Consent-gated canonical challenge
responder", identikey-core 296420d cited code, Mjolnir b8033c3 edge-auth
spec + `edge_keys.ex` / `login_profile.ex`, `direct_challenge.rs` @ 696fb00.

1. Audience: `ChallengeAdmission::parse` requires 64-hex `aud`, and the living spec says so. Mjolnir `verify_response(.., pinned_edge_xid: &str ..)` compares strings, and the edge text form is base58. Every real edge Challenge fails admission today. Pin: `aud` is base58 that decodes to exactly 32 bytes and re-encodes byte-identically (the same check as Mjolnir `canonical_edge/1`). Refuse hex, and refuse hex-or-base58 as a fallback.
2. Bind bytes: core signs exactly `bind_signing_bytes` @ 696fb00. That is the 7-array `["identikey-mjolnir/v1","bind", challenge bstr, ClassicalPublicKey::to_value().to_bytes(), op tuple, resource tuple, channel bstr32]`. Pin a byte vector that is shared with the Mjolnir test, not one re-derived in core.
3. Consent covers the bind: session public key, operation, resource, and channel enter the consent digest. Use a new domain tag so that an old digest cannot authorize a bind. All of these fields are fixed at begin and immutable afterwards. Finish rebuilds the bind from the stored row. It does not take caller bytes.
4. The bind's challenge field is the attempt's stored Challenge bytes, never a caller value. The bind and the Response come from the same key in the same attempt. Both are stored in one commit, and retrieve releases both or neither. `indeterminate` covers the pair.
5. Validate the tuples the way Mjolnir `CanonicalTuple::new` does: nonempty, components nonempty, 0x21..=0x7e. Channel is exactly 32 bytes and opaque. Core does not check it (steer: the edge checks it).
6. Session key: Ed25519 32 B or P-256 33 B only. Refuse a session key equal to the managed operational public key.
7. The managed key signs only two server-built structures. It never signs caller-chosen bytes.
8. Refuse: a bind without a Response in the same attempt, a second bind on a completed attempt, and a bind added at finish or retrieve.
9. Open question: A3 WebAuthn shows the user nothing about operation or resource, so "consent covers the bind fields" is a cryptographic commitment, not an informed display. The author should say which one this is.
10. Tradeoff: core now hard-codes a Mjolnir-specific payload. That gives interop now, but it couples core to one RP's format. A generic protocol-level bind would mean waiting on identikey-protocol. I would accept the coupling if the format is named and versioned and its domain cannot collide with identikey-auth signing bytes.

## Steelman against my take

**A. Keeping `identikey-managed-consent-v1\n` instead of a new tag.** My take asked for a new tag. The contract's choice is sound for four reasons:
- The old transcript is length-framed: `u32 len || challenge` comes before the fixed-width `commitment(32) || iat(8)`. A new transcript is therefore the old transcript plus a non-empty suffix, and no input to one equals an input to the other.
- No code path computes the old transcript after this change (D7).
- Pre-migration rows fail closed at finish.
- An A4 wallet still on the old transcript recomputes `13ef…`, sees the mismatch, and refuses to sign.

A new tag would be tidier, but it buys no security here, and it would cost one more re-pin. I withdraw item 3's tag request.

**B. Ed25519-only session keys.** The narrower choice is safer than my take. It also fixes the map at 51 bytes, which keeps field 7 unambiguous without a length prefix. If P-256 is admitted later, CBOR self-delimiting and the counted fields after it keep the transcript injective.

**C. The caller renders consent.** A WebAuthn prompt cannot show `operation`/`resource` whatever the OP does. A hosted page would need a browser hop, which the native direct path exists to avoid. Under the steer (wallet parity, one tap), D6 states the residual honestly, and the edge's policy check is the real limit on what a misrender can authorize.

## Notes (non-blocking; for act or fold, no re-advise needed)

1. **Channel provenance is misdescribed. The OP's behavior is unaffected.** D2 says the channel is "what the edge handed the client beside the Challenge". The delta scenario "Channel is not checked here" says the client "copied [them] from an edge Challenge". Mjolnir edge-auth "Channel binds the current authenticated peer" says something else: the gateway returns `server_conn_id` beside the Challenge, and the channel is `Blake3(SPKI(origin cert) || server_conn_id)`, or `Blake3(peer_iroh_node_id || conn_id)` for Iroh. A v1 Challenge has no channel field. Relay detection only works if the client derives those 32 bytes from its own view of the TLS/Iroh peer. A client that copies 32 bytes from the edge loses relay detection. The OP still signs opaque 32 bytes either way, so no byte, vector, or check changes. Reword to "the 32-byte channel binding the client derived for its edge connection (edge-auth Channel requirement)", so that a `mjolnir-22ff.6` implementer reading core's living spec does not copy bytes instead of deriving them.
2. **The non-canonical base58 clause has no constructible GIVEN.** Base58 (Bitcoin alphabet, leading `1` = zero byte) is a bijection: every string that decodes to 32 bytes re-encodes to itself. A 200k-sample fuzz found none, and the argument is two lines (leading `1`s fix the zero-byte count, and the remainder has no leading zero digit). Keep the re-encode guard as defense-in-depth that matches Mjolnir. Test refusal with cases that can exist: a string with an extra leading `1` (33 B), a string too short (31 B), a disallowed character (`0`, `O`, `I`, `l`), and a 64-hex string (47 B). Label them as such. Do not search for a vector that cannot exist.
3. **Make the separation assertion structural.** The identikey-auth `signing_payload` is `dcbor([CONTEXT, "challenge", chal])`, which starts with `0x83`. `bind_signing_bytes` starts with `0x87`. They cannot be equal for any input. Assert the leading byte and array arity, as well as the joint-vector inequality the delta requires.
4. **Admission caps are core-only.** The 8-component and 64-byte caps are stricter than the edge. If a future Mjolnir resource id exceeds 64 bytes, C2 users get refused at begin while wallets succeed. That would break the steer's stated wallet parity. Record the caps beside `mjolnir-22ff.4`/`.6`, so that the edge's resource naming stays within them or the caps move together.
5. **Optional:** refuse `session_public_key == operational public`. The capability that results is unusable rather than dangerous, because the OP never signs Mjolnir holder-proof bytes. Refusing it is still a cheap way to stop a confused client from binding a session to a key it does not hold.

## Verdict

Accept. Every concern in the blind take has an answer in the contract, or a steelman I accept. The two load-bearing pins check out independently: the joint bind vector matches Mjolnir `696fb00` byte for byte, and both consent digests recompute to the pinned values. The audience fix closes the gap that would otherwise have refused every real edge Challenge. Notes 1–5 are wording and test-shape fixes. They change no signed bytes. The implementer may proceed on this contract.
