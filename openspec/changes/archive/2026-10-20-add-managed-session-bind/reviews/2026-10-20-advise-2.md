## Blind take (written before opening design/tasks/steer/specs/reviews)

1. Pin: the bind signer is the same stored Ed25519 operational key that signs the Response (`verify_and_issue` checks `identity.public_key`); one claim, one decrypt, both signatures, one result commit.
2. Pin: bind bytes are exactly Mjolnir 696fb00 `bind_signing_bytes` (7-array, `identikey-mjolnir/v1`, `bind`, verbatim Challenge bstr, `ClassicalPublicKey::to_value()` map, two text-tuples, 32-byte channel), with `direct_challenge_canonical_bind_vector` copied verbatim as a core test.
3. Pin: the server builds the bind from typed fields; no caller-supplied signing payload, no holder public key; the Challenge bstr is the stored attempt's bytes.
4. Pin: consent digest gains a new domain tag (not v1) committing the bind fields with length/count framing, so no v1 (no-bind) consent can authorize a bind and no bind consent maps to a different tuple.
5. Pin: admission before decrypt mirrors the edge: `CanonicalTuple` rules (nonempty, 0x21..=0x7e per part, nonempty list), session key Ed25519/32 or P256/33, channel exactly 32 bytes; all immutable on the attempt row.
6. Refuse: verifying the channel or session-key possession at the OP (edge owns both); a separate bind-only endpoint/ceremony; a second encoding "close to" Mjolnir's.
7. Refuse: releasing Response and bind separately (retrieve returns both or neither); a bind on a C1/Schnorr row; account cookie as consent.
8. Ask: is the bind optional on begin (Response-only stays valid) and is a bind-less attempt distinguishable in the audit row?
9. Ask: audit records operation/resource/session-key fingerprint so the user can see what was authorized.
10. Tradeoff: port the ~40-line encoder into core pinned by vector (fast, drift risk) vs. move it into identikey-auth/protocol and depend on one implementation (no drift, cross-repo coordination). I'd accept the port only with the vector test and a named owner for the shared move.

**Steelman on 4.** I would have bumped the tag. The author's choice still holds. The old transcript ends in a fixed-width `iat`. The appended fields are a self-delimiting CBOR map, count/length-framed tuples, and a fixed 32-byte channel, so the new preimage is injective. Pre-migration rows fail closed (N3 of the prior review). A wallet that still computes the six-field digest gets a mismatch and refuses. No consent can be misread across the two forms, so a tag bump is hygiene only.

**Steelman on 8.** I asked whether bare begin should stay. D7 is right. Mjolnir is the only consumer, and Mjolnir will not mint from a bare Response. A dual mode would put a bind-less attempt and a bind attempt in one ceremony. Mandatory is the smaller attack surface. The cost: C2 now answers identikey-auth Challenges only inside the `identikey-mjolnir/v1` bind domain. A second RP that wants a C2 edge proof needs a new change. I record that as an accepted tradeoff, not a defect.

## Blocking

**B1 — The edge Challenge `aud` form is unpinned, and the likely form fails OP admission.** The base requirement this change MODIFIES keeps admission at "64-hex `aud`". The archived responder design (Decision 2) says 64-lowercase-hex. On the edge side, `verify_and_issue` calls `verify_response(response, context.pinned_edge_xid, …)`, and identikey-auth compares `challenge.audience` to that string exactly. Mjolnir's canonical text form of the edge XID is base58: `EdgeKeys.edge_xid_text/1`, and `LoginProfile.canonical_edge/1` accepts only 32 raw bytes or base58 text that round-trips. The protocol `encoding-conventions.md` and this repo's CLAUDE.md both say an XID text boundary is base58btc and hex is diagnostics only. The edge's Challenge issuance (`mjolnir-22ff.4`) is not written yet, so nothing pins `aud` across the two repos. If the edge follows its own convention, every edge Challenge fails at `begin` with `ChallengeAdmission("audience format")`, and the ceremony this change builds has no working consumer. If the edge issues hex instead, it breaks the stack's encoding rule and nobody recorded that. This is the same class of joint-contract gap as the prior B1 (string vs tuple). It lives in the admission clause rather than in the bind.

Fix: pin the edge Challenge `aud` text form in this change's delta and design. I recommend base58btc of the 32-byte edge XID, admitted only if decode-then-encode round-trips (mirroring `canonical_edge`). State whether 64-lowercase-hex stays admissible or is withdrawn. Add a scenario and test: an edge-shaped Challenge with that `aud` passes `begin`, and a non-canonical one is refused before the row is stored. Record the pin as owed on `mjolnir-22ff.4`, so the edge issues that exact form, rather than leaving it implied. Leave the internal A4 consent Challenge `aud` (`xid_hex`) as it is. Changing it would re-pin the consent vector, and it never reaches the edge. Say that explicitly so nobody "fixes" it later.

## Non-blocking

- **N1 — Name the encoder as a port.** identikey-core does not depend on `mjolnir_biscuit`, so "builds `bind_signing_bytes` from Mjolnir `696fb00`" is a re-implementation. That is acceptable only because Mjolnir's own vector is copied verbatim. Say it is a port pinned to `696fb00`. Say the `identikey-mjolnir/v1` string is the version, so any change to the edge encoding must bump it. Name where a shared home would go later (identikey-auth or the protocol repo). Without this, a later edge edit that keeps the tag would leave the core vector green and the bytes drifted.
- **N2 — Retrieve `bind` vs `ClassicalSignature`.** The edge `SessionBind.signature` is a `ClassicalSignature {alg, sig}`. D8 returns 64 raw bytes while `session_public_key` is returned as a map. Either return `{alg:"ed25519", sig}` for parity, or state that the client wraps with `alg` `ed25519`.
- **N3 — List the bind columns as immutable.** For A3, the consent binds by the server row (a library WebAuthn challenge), not by the digest. So for A3, the row is what makes the bind fields consented. The delta says finish takes nothing from the client, but the living "immutable account, challenge, request id, and a PKCE verifier commitment" list does not name the four bind fields. Add them.
- **N4 — Proposal wording.** The proposal says "Consent shows those plus the channel bytes". D6 changed that to "the caller renders, from bytes begin returns". Align the proposal.
