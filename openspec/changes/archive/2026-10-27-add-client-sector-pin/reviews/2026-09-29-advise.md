## Independent blind take

1. Pin the exact sector bytes currently supplied to the subject seam; pinning a newly chosen name would change every pairwise subject.
2. Both primary environment configuration and JSON clients must carry the pin through the same construction path.
3. Existing clients need an explicit migration inventory based on the effective first redirect after merging, including any historical `default` fallback.
4. Refuse missing or invalid pins only with a rollout sequence that accounts for one malformed client stopping the whole provider.
5. Preserve the salt, XID encoding, subject type defaults, and KDF unchanged; sector selection is the only intended seam change.
6. Redirect additions, removals, replacements, and reordering must leave the pinned sector and resulting subjects unchanged.
7. Define whether sector values are opaque bytes or normalized hostnames; silently trimming or canonicalizing a historical value risks identity changes.
8. Public subjects must remain the XID and must not acquire an unnecessary sector dependency.
9. Prove old-versus-new subject equality with fixed salt/XID and actual legacy construction, including both configuration entry points.
10. The tradeoff is stronger identity continuity versus stricter startup availability; distinguish redirect independence from detecting an operator changing the pin itself.

## Verdict and comparison

Send back for two bounded migration-contract fixes. The proposed implementation shape is sound; neither finding requires the registry, signing, dynamic registration, or a new persistence layer.

The author answers blind concerns 2, 4, 6, and 8 directly: both configuration surfaces get a sector, missing/empty pairwise sectors fail startup, redirects stop supplying the sector, and public clients need none. The existing subject seam and KDF can remain untouched. Concerns 1, 3, 7, and 9 need stronger acceptance criteria before implementation is unblocked.

### R1 — High: validate the complete migration before switching binaries

Evidence: `design.md:20–28` checks escrow/guest equality only for `IDENTIKEY_CLIENTS`, restarts an old binary that ignores the new fields, then compares only taskmaster and Conduit subjects after deployment. `tasks.md:7` scopes the helper to JSON clients. The primary client is loaded independently (`crates/identikey-server/src/main.rs:1112–1128`), and any client-loading error propagates before listener binding (`main.rs:1249–1266`).

A successful old-binary restart cannot establish that the new binary will accept the pins: an omitted primary sector or wrongly typed JSON sector remains invisible to the old loader. A nonempty but incorrect pin passes the proposed new startup check and changes identities; the two post-deploy probes also leave taskmaster-laptop and wtnf-web unchecked. Hash agreement between two JSON copies does not verify the primary configuration or prove that either copy reflects the running process's effective registration.

Amend the rollout to inventory the effective primary registration and JSON registrations, including subject types and redirect precedence, against both escrow and guest configuration. Before cutover, require the candidate loader to accept the complete proposed configuration and require every effective pairwise client's proposed sector bytes to equal its legacy-derived bytes. This can be a local/offline preflight using the same parsing path; no new production endpoint is required. Exact sector equality plus an unchanged salt/XID/KDF establishes continuity for every person, so live browser probes need not be multiplied across all clients. Capture the taskmaster/Conduit subject baseline before the first mutation, explicitly preserve the deployment's salt, and record backup/abort/rollback steps. Keep the existing human gate. Failed preflight must stop deployment while the old service remains available.

### R2 — Medium: make legacy byte preservation executable

Evidence: `design.md:22–24` specifies the first redirect's host, while the actual `sector_from_redirect` (`main.rs:1052–1057`) uses `url::Url::parse(...).host_str()` and returns the literal `default` when parsing fails or no host exists. `merge_redirects` (`main.rs:1099–1110`) drops empty entries and gives the singular `redirect` precedence. `tasks.md:5` tests only stability after pinning. The delta's prohibition on deriving a sector also needs an explicit exception for the migration helper already required by the design.

A helper that rejects a formerly accepted hostless redirect, chooses the first `redirects` element despite a singular `redirect`, or canonicalizes an already-derived pin differently can either prevent migration or mint a different subject. State that pins are stored and passed verbatim to the KDF, with explicit missing/empty handling; make the helper reproduce the legacy parser, merge ordering, and `default` fallback exactly. Clarify that redirect derivation is forbidden in runtime client construction, but intentionally permitted in the migration helper.

Add deterministic old-versus-new subject equality tests using fixed salt/XID for primary and JSON configuration, omitted/default pairwise subject type, singular/plural redirect precedence, host normalization, and hostless/parse-failure fallback. Include the four documented live pairwise shapes as sanitized fixtures. Exercise redirect replacement/removal as well as addition/reordering, empty/missing pin rejection, and public-subject equality without a sector. These tests must compare against legacy outputs, not only compare two executions of the new path.

## Steelman against the blind take

The strongest case for acceptance is the deliberately small change: `Client.sector_identifier` already exists, the author preserves the subject seam, and freezing the existing value decouples redirects without introducing a database. Strict startup refusal is a defensible, explicitly acknowledged availability tradeoff; an implicit fallback would perpetuate the identity hazard. Reusing the existing helper is also a credible way to preserve parsing behavior.

Those points narrow the findings to verification and rollout, rather than a competing design. The old binary's tolerance is useful for staging configuration but cannot validate the new contract. Redirect-independent subjects alone do not establish migration continuity. Once R1 and R2 are incorporated, this shape merits a fresh review. Detecting arbitrary later operator edits to a nonempty pin remains outside this node; document that boundary rather than inventing registry enforcement here.
