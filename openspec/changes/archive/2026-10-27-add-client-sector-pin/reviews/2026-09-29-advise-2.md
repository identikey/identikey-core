## Steelman against the independent take

My blind take emphasizes refusal and byte preservation, but refusal alone can cause a provider-wide outage. The author's bounded solution is stronger than merely making the setting mandatory: validate the whole proposed configuration using the candidate's actual loader before touching the running service. Keeping pins opaque also deliberately permits historical `default` and shared loopback sectors. Replacing those with cleaner or per-client values would break continuity; stricter hostname validation is not warranted in this node.

There is no need to add persistent pin history, a registry, or signed records to close these findings. The contract acknowledges that later operator edits to a nonempty pin can change identities, while this node removes redirects as an implicit source of those edits.

## Amendment risk and operational boundary

The new command is an operator migration comparison, isolated from boot and requests and specified to need no database, network, or salt. It must preserve that separation when implemented. After a legitimate future redirect-host change, `check-clients` can report a legacy mismatch even though the pinned identity is correct; its comparison is not an instruction to repin or a permanent runtime gate. Similarly, the documented old-binary rollback is safe for this initial pin-only cutover, while the historical redirect configuration is retained. It is not a promise that an old deriving binary remains safe after later redirect edits.

Boot refusal still affects every RP. The complete preflight and staged rollout address that accepted availability tradeoff without retaining a silent derivation fallback. No amendment introduces another runtime subject-computation path.
