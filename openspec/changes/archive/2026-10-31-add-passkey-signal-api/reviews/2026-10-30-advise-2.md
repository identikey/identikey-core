## Blind take (before the amended contract)

1. Handle: unpadded base64url of the 16 bytes of `xid_user_id`. Test it against `user.id` from `register/begin`, not against a fixture.
2. Id: unpadded base64url of `webauthn_credential_id`. Test it against the posted `credential.id`.
3. Stored means `kind = 'passkey' AND revoked_at IS NULL`. A revoked passkey offered again is unknown, and that is correct.
4. If the list is missing or empty, the page makes no accepted-list call. If the list read fails, the success still stands.
5. The call is not awaited, or is awaited with a bound. A sync throw, a rejection, and a promise that never settles all still navigate.
6. Foreign XID: `ceremony_http` sends `err.to_string()`, and both `pages-login.js:61` and `pages-common.js:88` match on that string. So the split needs a new variant with a *different message*, not only a different variant name.
7. Splitting the error tells the caller that the credential id exists on some account. That is acceptable: a bound `begin_assert` already lists a XID's ids in `allowCredentials`, and ids are random. The design should not have to say so, but act must not mistake the split for a leak and merge it back.
8. `encapsulation.rs:132` maps `UnknownCredential` from `begin_managed_assert` (no passkeys) to a decoy challenge. The split must touch only the *finish* foreign-XID branches. If it also changes begin, that decoy breaks.
9. Localhost: skip `signalUnknownCredential`, and key the check on the RP ID in the ceremony options, not on `location.hostname`.
10. Tradeoff: a distinct error versus signaling only from unbound ceremonies. The distinct error still holds when a future change wires `params_xid_from_query`. I would pick it.
