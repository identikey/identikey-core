## Blind take (before the contract)

1. Pin the user handle on the wire: unpadded base64url of the 16 raw bytes of `xid_user_id(xid)`, the same value as `user.id` in creation options. Not the UUID string or the base58 XID.
2. Pin credential ids as unpadded base64url of `webauthn_credential_id`, the same string the page posts as `credential.id`.
3. "Stored" means a live passkey: `kind = 'passkey' AND revoked_at IS NULL` (`list_passkeys`). Never `ssh_git` rows, never revoked ids.
4. Never call `signalAllAcceptedCredentials` with an empty list, because an empty list tells the provider to hide every passkey for that handle. A failed list read after an accepted ceremony must not fail login.
5. The RP ID comes from server config (the ceremony options), not `location.hostname`.
6. Catch a sync throw *and* an async rejection. Do not await an unbounded promise before `location.assign`.
7. Refuse `signalUnknownCredential` when the row exists but belongs to another XID. `finish_assert` and `finish_managed_assert` return the same `UnknownCredential` in that case.
8. Refuse to let the dev OP (`localhost:8080`, `identikey-core-sqlx`) and `identikey-local` (`localhost:8070`, `identikey-local`) delete each other's passkeys. Both use RP ID `localhost` with different credential stores.
9. On the device page, send the list only on `{"approved": true}`. `finish_assert` uses up the session before the `confirmed` check.
10. Tradeoff: awaiting the signal makes delivery more reliable but lets a slow provider extension stall the redirect. Firing it unawaited, right before navigating, can drop the hint at unload. I would fire, attach `.catch`, and navigate, and accept a lost hint.

## Compare

**What the contract already covers.** It answers 5 (design: "the RP ID
is the one already in the ceremony options") and 9 (proposal: device
approval "has no redirect; it still receives the list", and other
failures signal nothing). It also gets the most important call right:
the accepted list is *every* id, not the one used (steer, design
§Calls). The delta's "only after the server has accepted the
ceremony" and "SHALL NOT treat either call as authorization" are the
right guards. Keeping `signalCurrentUserDetails` and removal out of
scope is correct: `user.name` is the XID and nothing renames it.

**Steelman.** One could argue points 1–3 are implementation detail
and act will get them right. Point 7 cannot happen from any hosted
page today: `/authorize/passkey` calls `begin_assert` with
`params_xid_from_query`, which always returns `None`, and the device
page is discoverable. Point 8 only matters on a laptop. I accept that
1–3 are cheap. Even so, a wrong encoding makes the feature a silent
no-op that no test in the current task list would catch. "Swallowed
throw" tests a synchronous throw, and a stub can pass with any string.

**Gaps the author still owes.**

- **Empty or missing list.** The design says the list is loaded
  "after the row write". It does not say what happens if that read
  fails, or if the list comes back empty. One choice is to 500 after
  `issue_code` or `approve_device` has already succeeded. The other is
  to send `[]`, which the provider reads as "drop all of this user's
  passkeys". The first changes whether the person got in, which the
  Why forbids. The second is the most destructive call this feature
  can make. Both need a SHALL.
- **Async rejection and hangs.** The design says "a missing function
  or a thrown exception is swallowed", and that the call happens
  "before it navigates". The signal methods return promises. If the
  page awaits one that never settles, the redirect never happens. If
  it does not await and does not `.catch`, rejections surface as
  unhandled. Pin "not awaited, or awaited with a bound" and test a
  promise that never settles.
- **Unknown versus foreign.** The delta says "because the credential
  is not stored", which is correct. The task keys the call on the
  message `credential not found`, and the server sends that same
  message when the row exists for another XID (`ceremonies.rs`
  `finish_assert` `bound != stored.xid`, and `finish_managed_assert`).
  Today no hosted page reaches that branch. The first change that
  wires `params_xid_from_query` or a bound account assertion would
  turn this hint into deleting another account's valid passkey. Split
  the error, or limit the signal to unbound ceremonies, and test it.
- **Shared `localhost` RP ID.** Per CLAUDE.md, `.env.example` and
  `install-local-op.sh`, two OPs on this machine use RP ID `localhost`
  with separate databases. A passkey minted on `identikey-local`,
  offered on the dev OP, gets `credential not found`. The dev page
  would then tell iCloud Keychain, Google Password Manager or
  1Password to remove a passkey that is valid on the other OP.
  Accepted lists do not cross, because the handles are per-XID, so
  only the unknown signal is at risk. Loopback cannot use any other
  RP ID, so the answer is a decision, not a rename. Recommended: do
  not call `signalUnknownCredential` when the RP ID is `localhost`.
  The other option is to write down that the local pair accepts this.
- **Encodings and "stored".** Points 1–3 above. The tests should
  check the handle against `user.id` from `register/begin` and the id
  against the posted `credential.id`, not against a fixture string.
  Revoked rows already fail `get_passkey_by_credential_id`, so a
  revoked passkey that is offered again is reported unknown. That is
  correct, and it is the only removal path this slice has. Write it
  down so act does not treat it as scope creep into `5gh.6`.

Not owed: shape of the RP ID field (the options already carry it),
pages other than the three named, and the `{"xid"}` API branch of
`assert_finish`. That branch may carry the list or not; no page reads
it.

## Verdict

Send-back. The direction is right and the change is small. But two
gaps go against the Why: an empty list, and a signal that is awaited
without a bound. Two more can delete a passkey that is valid: the
foreign-XID branch and the shared `localhost` RP ID. Owed checkboxes
are added under "Owed from advise 2026-10-30" in `tasks.md`.
