Reviewed 2026-10-27 against HEAD `65bcba4`. Disposition: `task-red`.

The architecture is sound: verified registration writes presentation metadata,
the account page resolves a local pin, and ceremony loads omit the presentation
AAGUID. The current contract needs three bounded corrections before acceptance.
This is not a request to redesign authentication or expand passkey management.

## Blind pass

I wrote the [ten-line independent take](2026-10-27-astra-blind-take.md)
after reading the proposal, living passkeys spec, and cited code, and before
opening the design, delta, or tasks. Its concerns were: presentation-only trust;
post-verification extraction; backup-state meaning; nickname precedence; offline
metadata provenance and fallback; inert escaped rendering; session and account
isolation; legacy/empty states; reconciliation with already-landed code; and the
tradeoff between a stale compact pin and private, deterministic display hints.

## Comparison and steelman

The delta correctly **adds** “Passkey rows name the authenticator”; no such
requirement exists in the living spec. It modifies the existing first-party
profile requirement and preserves its OIDC and signed-out scenarios. It leaves
the living registration/assertion requirement intact.

The best case for accepting this now is that the code already supplies most of
the detail the short design omits. `ceremonies.rs:181-200` verifies the response
before extracting metadata and writing through `insert_passkey_with_metadata`.
The parser returns absent metadata rather than an authentication error.
`store.rs:527-572` loads ceremony credentials without selecting the presentation
AAGUID. `main.rs:514-567` resolves the account session before fetching that XID's
non-revoked presentation rows; those rows contain no key material.
`passkey_metadata.rs:12-64` embeds the pin and filters icons to embedded SVG data
URLs, and `pages.rs:175-200` escapes rendered values. These answer the trust,
privacy, and isolation concerns without requiring new abstractions.

I also withdraw any implied demand for a live provider service, full device
identification, automatic pin refresh, or a nickname-editing UI. A compact
vendored list and nickname input accepted only by the existing finish API are
reasonable within this slice. Registration-time backup information can also be
a reasonable bounded choice, provided the contract states its limits.

## Owed corrections

1. **Resolve the contradictory nickname fallback contract.** Delta lines 8-10
   require nickname precedence, but lines 12-14 unconditionally require
   “Passkey” for missing/unreadable metadata. The unknown-AAGUID scenario at
   lines 31-36 also lacks a no-nickname precondition. For a saved nickname
   “Work key” and an unknown AAGUID, `pages.rs:176-184` correctly keeps “Work
   key”. Qualify the generic fallback to apply only when no nonempty nickname
   survives, and cover nickname-plus-unknown/unreadable metadata as well as
   blank nickname behavior. The design repeats the ambiguity at lines 18-20.
   Steelman: the precedence sentence conveys the intended behavior; nevertheless
   the two unconditional SHALLs currently demand different output for one input.

2. **Define the backup-state display contract.** `ceremonies.rs:484` extracts BS
   at registration. `store.rs:617-621` updates only counter and last-use time on
   assertion; `store.rs:604-606` maps legacy NULL backup state to false, and
   `pages.rs:187-191` renders false as “Not backed up”. The delta says the row
   shows whether the passkey *is* backed up, without defining snapshot freshness
   or legacy unknowns. State explicitly whether this slice exposes the
   registration snapshot or maintains status, and define what missing/legacy
   metadata means to the person reading the row. Pin BS rather than backup
   eligibility. Snapshot semantics are acceptable; adding assertion-time status
   maintenance is not a prerequisite I am imposing. Unknown must not silently
   become a claim of observed negative status. Align the chosen contract, display
   expectations, and focused verification through the author/executor workflow.

3. **Close the actual ceremony-evidence gap.** `tasks.md:8` marks a ceremony
   accepting two AAGUIDs as tested. The cited test at `store.rs:1503` inserts
   placeholder key JSON and checks persistence and lookup; it never verifies an
   assertion. The parser tests at `ceremonies.rs:607-631` likewise exercise only
   metadata extraction. Those are useful tests, but do not execute the delta's
   “WHEN either one asserts” scenario. Supply focused evidence through the real
   assertion path for two valid credentials with different stored presentation
   AAGUIDs, or explicitly reconcile the promised verification before claiming it
   complete. Static inspection supports non-gating behavior; it does not turn a
   store lookup test into the already-claimed ceremony test.

## Reconciliation notes

The proposal's preparation paragraph still describes a count-only page and
dropped metadata. The design names `insert_passkey` as the metadata write,
although that compatibility wrapper supplies empty metadata and registration
actually calls `insert_passkey_with_metadata`. These should be corrected when
the author reconciles the documents; they are not evidence of missing product
implementation. Likewise, “registration does not read the AAGUID” should mean
“does not use it for acceptance”, since registration necessarily extracts it for
storage. The local metadata pin records a source URL and date, but only contains
three providers; document that compact scope and preserve reproducible source
provenance when refreshing it.
