## Blind take

I wrote this from the Why, the living `passkeys` spec, and the cited code, before
opening design.md or tasks.md.

1. Pin one shared verdict function (Fresh / Zero / Regressed / Repeated), called by
   all three sites, with a table test.
2. Pin that counter 0 never lowers the stored `sign_counter`. Today all three sites
   write the presented 0 over a positive stored value.
3. Pin a monotonic store write. `finish_assert` and `finish_managed_assert` read
   `sign_counter` and write it later without a lock, so two concurrent ceremonies
   can lower the floor.
4. Pin webauthn-rs. `webauthn-rs-core` 0.5.4 hard-codes
   `require_valid_counter_value: true` (`core.rs:215`, and `webauthn-rs` has no
   setter). It compares the presented counter against the `Passkey` JSON counter,
   which is frozen at registration. Any presented counter at or below a positive
   registration counter fails inside the library before our rule runs. That
   includes 0.
5. Refuse "fixing" item 4 by calling `Passkey::update_credential` on
   `passkey_json`. That raises the library's floor and turns every drop back into
   a reject.
6. Pin what the drop log carries and how a test sees it: a returned verdict, not
   scraped output.
7. Pin the equal-positive reject's error. It is a clone signal, not replay:
   single-use challenges already stop replay.
8. Refuse any change to how registration seeds the counter (the column starts at 0).
9. Tradeoff: the equal-positive reject fails closed against clones, but it locks
   out any authenticator that reports a constant nonzero counter. Accept that and
   name it.
10. Tradeoff: keeping the stored value on a drop holds the clone floor high, so a
    cloned copy that has fallen behind keeps logging after the original climbs.

## Compare

The proposal, delta, design, and steer cover items 1, 6 (partly), 7, 8, 9, and 10.
The single helper in design "Sites" answers item 1 directly. Steer records the
high-water-mark decision ("The stored counter stays at the high-water mark"),
which is the principle behind items 2 and 3. Items 2, 3, and 4 are not carried
through to the contract.

### Owed 1: counter 0 over a positive stored value lowers the floor

design.md line 9 says: "The stored value may already be 0; writing 0 again is
harmless." That holds only when the stored value is 0. Here is the case it misses:

- The `Passkey` is registered at counter 0, so webauthn-rs skips its check when 0
  is presented.
- The column has since climbed to 10.
- The authenticator now reports 0. A provider can stop counting after a sync or
  an import.

The new rule accepts that assertion. If the site keeps calling
`update_passkey_sign_counter(cred, 0)`, which is what "writing 0 again is
harmless" invites, the column drops to 0. A cloned copy that later presents 5 then
reads as an increase. That breaks steer's high-water-mark decision.

The delta has no scenario for it: "Zero is not a regression" only covers stored 0.
The fix is one scenario (stored 10, presents 0: succeeds, stays 10, no drop log)
and a write that never lowers the value.

### Owed 2: the store write must be monotonic and still bump `last_used_at`

`KeysStore::update_passkey_sign_counter` (`store.rs:612`) writes
`sign_counter = $2, last_used_at = now()` unconditionally, and the hosted and
managed paths call it after an unlocked read. Two concurrent assertions on one
credential can each be checked against 10. Say they present 12 and 11 and the 11
write lands last. The floor is now 11, below a value already seen. The
encapsulation path holds `FOR UPDATE`, so only the two server paths race.

The obvious way to "not write the lower value" is to skip the call on a drop. That
also stops bumping `last_used_at`, which `/account` shows (`main.rs:556`). The
synced passkeys this change exists for would then show a stale "last used" date.

One write covers all three problems: owed 1, the race, and `last_used_at`. Write
`sign_counter = GREATEST(sign_counter, $2), last_used_at = now()` on every accepted
assertion, at all three sites. This changes a `query!`, so `.sqlx/` needs
regenerating, as CLAUDE.md requires.

### Owed 3: the delta promises acceptances that webauthn-rs refuses

This is item 4. With 0.5.4 as configured, `finish_passkey_authentication` and
`finish_discoverable_authentication` return `CredentialPossibleCompromise` when the
presented counter is at or below the counter in the `Passkey` JSON (whenever either
value is nonzero). `passkey_json` is never updated after registration: there is no
`update_credential` call anywhere in `crates/`.

So for a credential whose registration counter N is above 0:

- presenting 0 fails, although the delta says 0 "SHALL be accepted";
- a drop to a value at or below N fails, although the delta says a drop "SHALL be
  accepted".

The new helper never sees those assertions. The tests in tasks.md will not catch
this: they seed the column directly, and a soft authenticator registered at 0
never reaches the library check.

The synced providers named in the Why mostly register at 0, so the main population
is fine. But a SHALL the binary contradicts must not fold into the living spec. The
author must choose one of these:

- **(a) Hand the counter decision to our rule.** Before webauthn-rs sees the
  `Passkey`, set its counter to 0: in `load_passkeys`, in the discoverable
  `DiscoverableKey`, and in the state stored for managed and encapsulation
  ceremonies. The library then never rejects on counter, and the column plus the
  helper are the only counter authority. This is a counter policy, not a signature
  check, so it stays inside the proposal's out-of-scope line ("Changing webauthn-rs
  signature checks"). It needs one test with a credential registered at a positive
  counter.
- **(b) Scope the SHALL.** Add a sentence such as "after webauthn-rs accepts the
  assertion" to the delta and the proposal, and name the positive-registration
  case as still rejected, with the reason.

I lean toward (a). It makes "one helper, so a later call site cannot keep the old
reject" true, which is design's own goal. Either option is acceptable.

## Steelman against my take

- *"Item 4 is existing library behavior and out of scope."* It is existing
  behavior. But the delta becomes a living, unconditional SHALL. Option (b) costs
  one sentence and is enough; the send-back does not force (a).
- *"Owed 1 cannot happen: synced passkeys always report 0."* The column only
  climbs if the authenticator counted at some point. A credential that counted and
  then stopped is exactly the drop population the Why is about. The write that
  fixes owed 1 also fixes the race and the stale date, so it costs nothing.
- *"Item 3's race is too narrow to matter."* Alone, yes. It is in the box only
  because the same `GREATEST` write closes it.
- My item 6 (the log's fields and a test seam) is answered well enough. design.md
  names the fields, and the shared helper can return a verdict that tests assert
  on. Not owed.

## Notes (do not block)

- Steer records the user's 2026-09-26 words as "A counter that stays 0 or goes
  backwards is **logged** and accepted." The auto decision "Zero is not a
  regression log" then drops logging for 0. That is reasonable: every iCloud or
  Google login would log. But it changes something the user said, so the human
  should confirm it at act or fold.
- The Why and steer call the equal-positive counter "the replay signal". Replay of
  a single assertion is already stopped by single-use challenges: the session
  `remove`, the managed attempt state, and encapsulation's `used_at`. The equal
  counter is the clone signal. Fix the wording at fold; it does not change the
  rule.
- Log field: prefer the `credentials.id` UUID (or hex credential id, since this is
  diagnostics per encoding conventions) plus the base58 XID. Do not log the raw
  bytes `Debug`.
- I did not open the soft authenticator's counter behavior. Whoever writes the
  owed-3 test needs a way to register at a positive counter: seed `passkey_json`,
  or use an authenticator that starts above 0.
