## Blind take

I wrote this from the proposal Why, living `passkeys` spec, and the cited code,
before opening design.md or tasks.md.

1. Pin one counter authority. webauthn-rs-core 0.5.4 hard-codes
   `require_valid_counter_value: true` (`core.rs:215`). The high-level `Webauthn`
   has no setter for it.
2. Pin every place a `Passkey` reaches the library. The hosted Known path and both
   persisted states (managed via `managed_challenge.rs:169`, encapsulation via
   `encapsulation.rs:122`) come from `load_passkeys` through `begin_managed_assert`
   or `begin_assert`. The discoverable path builds its `DiscoverableKey` at finish
   from `passkey_json` (`ceremonies.rs:310`). Two choke points cover all three
   verifiers.
3. Pin how the counter gets zeroed. In 0.5.4, `Passkey.cred` is `pub(crate)`.
   `Credential.counter` is `pub` (`webauthn-rs-core/src/interface.rs:258`), but you
   can only reach it with the `danger-credential-internals` feature. The workspace
   enables `danger-allow-state-serialisation` and `conditional-ui`, not that one.
4. Pin a monotonic write (`GREATEST`) that still bumps `last_used_at` on every
   accept. Encapsulation's write today does not touch `last_used_at` at all.
5. Pin that 0 over a positive stored value neither lowers the value nor logs.
6. Refuse `Passkey::update_credential` on `passkey_json`.
7. Refuse treating the equal-positive reject as replay. Replay is the single-use
   challenge.
8. Pin a test with a positive registration counter. A soft authenticator at 0 never
   reaches the library check.
9. Note: states persisted before deploy still carry the registration counter.
   Their TTL is short.
10. Tradeoff: equal-positive fails closed against a tying clone but locks out any
    authenticator stuck at a constant nonzero counter. A lagging clone is only
    logged.

## Compare against the three owed items

### Owed 1: counter 0 over a positive stored value. Answered.

Delta lines 5-8: 0 is accepted "including when the stored counter is already
positive", SHALL NOT lower the value, and is not logged. The new scenario "Zero
over a positive counter is not a reset" is exactly stored 10, presents 0, stays 10,
no log, and `last_used_at` advances. design.md no longer says "writing 0 again is
harmless". It now says "Leave a higher stored value where it is." tasks.md line 12
is checked, and that is correct: it is a contract box, and the contract now holds
it.

### Owed 2: monotonic write that still bumps `last_used_at`. Answered.

Delta lines 13-16: every accepted assertion SHALL set `last_used_at` and leave
`sign_counter` at the greater of the stored and presented values. "A lower counter
still signs in" now requires `last_used_at` to advance. design.md "Store write"
names `GREATEST(sign_counter, presented)` and `last_used_at = now()` at all three
sites. It says why a drop must not skip the write (`/account`), and that `GREATEST`
is what closes the unlocked-read race on the hosted and managed paths. tasks.md
line 13 holds the implementation box, the `last_used_at` test, and the `.sqlx/`
regeneration. That covers my item 4, including encapsulation, which gains a
`last_used_at` it does not write today. "At all three sites" makes that explicit.

### Owed 3: webauthn-rs rejects what the delta accepts. Answered with option (a).

Delta lines 19-23: before webauthn-rs checks, the `Passkey` counter SHALL be 0.
`credentials.sign_counter` is the only authority, and `passkey_json` SHALL NOT be
raised. The new scenario "A registration counter above zero does not reject a later
drop" (registered 5, stored 5, presents 4: succeeds, stays 5, logged) is the test my
send-back asked for. design.md "Library counter" names `load_passkeys`, the
discoverable key, and the managed and encapsulation state, and forbids
`update_credential`.

I checked the claim against the library. With `cred.counter = 0`, the presented
value `c` enters the check only when `c > 0`. Then `c <= 0` is false, so
`CredentialPossibleCompromise` cannot fire. `AuthenticationResult::counter()`
still returns the presented value, so our rule sees the real number. The design's
list of sites matches item 2 of my blind take. The managed and encapsulation state
both come from `load_passkeys` through `begin_managed_assert`, so zeroing there also
covers "the state stored for managed and encapsulation ceremonies". The only other
entry point is the discoverable conversion at `ceremonies.rs:310`.

## Steelman against my take

- *"Item 3 is a hole: the contract says set the counter to 0, but 0.5.4 gives no
  way to do it."* It is not a contract hole. Two ways work, and both stay inside
  the contract: enable `danger-credential-internals` and go through `Credential`,
  or rewrite `cred.counter` in the serde JSON before deserializing. The spec states
  the observable outcome, and the positive-registration scenario tests it. Which
  mechanism to use is act's choice, not advise's. Recorded below as a note.
- *"Item 10 should block: the Why says counters 'do not climb', and a constant
  positive value doesn't climb either."* The first review accepted this tradeoff,
  and the user's 2026-09-26 words cover "stays 0 or goes backwards", not "stays
  positive". The delta now calls the equal reject the clone signal, and the Why
  says replay is the single-use challenge. Not owed.
- *"The equal-reject check reads unlocked, so two concurrent clones presenting the
  same value can both pass."* True on the hosted and managed paths. The contract
  promises a monotonic floor, not serialized clone detection. Concurrent clone
  detection is best-effort under WebAuthn's own model, and `GREATEST` keeps the
  floor correct. Not owed.
- *"Item 9 could lock someone out mid-deploy."* Only for a state begun on the old
  binary and finished on the new one, with a drop below a positive registration
  counter. The old binary rejects that today anyway. Not owed.

## Notes (do not block)

- Mechanism for zeroing (act): `Passkey { cred: pub(crate) }` in webauthn-rs 0.5.4.
  Either add `danger-credential-internals` to the workspace `webauthn-rs` features
  and round-trip `Passkey -> Credential -> Passkey`, or set `cred.counter` on a
  `serde_json::Value` before deserializing. Put it in one helper next to
  `load_passkeys` so the discoverable path cannot drift. That is the design's
  "one helper" goal, applied to the library side.
- Fold: living `openspec/specs/passkeys/spec.md` lines 10-11 still say
  "synced-passkey counter policy are later slices (`5gh.3`–`5gh.4`)". The delta is
  ADDED-only, so that intro prose will not change by itself. The folder should
  drop `5gh.4` from that sentence.
- Fold: steer.md lines 13 and 15 still say "replay signal" and "later replay of the
  old counter". The proposal, delta, and design now say clone. steer.md is a
  record, so leave it as is, but the folded spec should use the delta's wording.
- Carried from the first review, still for the human: steer records the user as
  saying 0 is "logged and accepted". The contract does not log 0. That is sensible,
  but confirm it at act or fold.
- Log fields: as before, use the `credentials.id` UUID or a hex credential id, plus
  the base58 XID, never the raw bytes `Debug`.
