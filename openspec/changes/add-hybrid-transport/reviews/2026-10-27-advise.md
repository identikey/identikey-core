## Blind take (written before design.md / tasks.md)

Sources: proposal Why/What, living `openspec/specs/passkeys/spec.md`
lines 13-22, `crates/identikey-server/src/ceremonies.rs`
`passkey_manager_compat` (lines 494-524).

1. Pin: hints are not transports. `hints` (WebAuthn L3 `security-key` / `client-device` / `hybrid`) is a UI preference, and `transports` belongs on credential descriptors. The What mixes the two: "`hybrid` hint, together with the other transports".
2. Pin: with no hints and no attachment, Chrome, Safari and Edge already offer "use a phone or tablet". The Why ("never ask for it") needs a named browser and case where hybrid is missing today.
3. Refuse: a hint list that leads with `hybrid`. L3 orders hints by decreasing preference. Chrome uses the first one it recognizes to choose its first screen, so desktop users with a local or synced passkey land on a QR screen. That is the same harm `passkey_manager_compat` exists to stop, arriving from the other side.
4. Pin: the rule is "no preference that hides another modality", not only "not just `client-device`". Write it as a property of the whole list, not a ban on one value.
5. Pin: the transports reported at registration (`getTransports()`) round-trip into `allowCredentials` / `excludeCredentials`, or are left out entirely (absent means any transport). An empty or partial list would hide hybrid.
6. Pin: `obj.remove("hints")` runs unconditionally. The insert must come after it, in one function, and be tested on both creation and request options.
7. Pin: the scope grows from creation options to registration **and** assertion. That is a MODIFIED delta and has to say so.
8. Refuse: "hybrid works" based only on a JSON-shape test. CI cannot do caBLE. Either record a manual phone check (browser and version) or state that none was done.
9. Tradeoff: adding hints buys a hybrid nudge on browsers that honour hints and costs the default sheet order for most users. Omitting hints is neutral and already compliant.
10. Exit test: unaffected (no custody or data change).

## Compare

What design / tasks / delta / steer answer:

- **Steer decides to add the hint.** Duke decided on 2026-09-26 to add the `hybrid` hint and not set `authenticatorAttachment`. Take item 9 ("omitting is neutral") does not overrule that. I am not re-arguing whether to add hints, only the order.
- **No caBLE, no QR route, no new encoding.** Answered in the design and the delta. Agreed.
- **Attachment stays absent and the discoverable credential stays required.** Answered. The existing test at `crates/identikey-server/src/main.rs:3105` asserts `hints` is null and has to flip. The implementer will find that, so no box is needed.
- **Client passthrough.** I checked this. `pages-signup.js` / `pages-login.js` / `pages-device.js` pass `decodePublicKey(structuredClone(publicKey))` to `navigator.credentials.*`, so a server `hints` reaches the browser and the change is not inert. Browsers without hints support ignore the member.
- **Transports (take item 5).** No defect today. `credToJson` (`pages-common.js:18`) does not send `getTransports()`, so webauthn-rs stores `transports: None`. `start_passkey_authentication` (`ceremonies.rs:219`, `:345`) then emits descriptors without `transports`, which browsers treat as "any transport, hybrid included". Keep it that way. If a later change starts sending `getTransports()`, it must store the full list. Not owed here.

What is not answered:

- **Hint order (take items 3 and 4). This is the blocker.** The design fixes the order as `hybrid`, `security-key`, `client-device`, and the delta scenario pins that exact order. Under L3 semantics that says the RP's first choice is a phone and its second is a USB key. In Chrome this makes the first screen the QR / phone sheet, ahead of the local Google Password Manager or iCloud Keychain passkey. The delta's own text promises the opposite ("without hiding a synced passkey provider"). The living requirement's intent (no list that prefers one modality and hides the others) is turned around, not kept.
- **The delta weakens the invariant.** The living text bans "hints that prefer a platform authenticator only". The delta replaces that with "a hint list that is only `client-device`". That is narrower, and it allows `["hybrid"]` or `["security-key"]` alone, which hide synced providers just as well. The invariant should be about the list, not one value.
- **Evidence for the Why (take item 2).** Nothing names a browser where hybrid is missing today without hints. If none exists, the user-visible change is only sheet order, and the order above makes that worse.
- **Acceptance (take item 8).** Task 5 tests JSON shape only. It does not say whether a real phone-to-computer ceremony was tried.

## Steelman against the take

- *"Listing all three means 'no preference'."* That would hold if browsers read a full list as neutral. L3 defines the list as ordered by preference, and implementations use the first entry. A full list in a chosen order is still a preference.
- *"1Password intercepts before the browser UI, so order cannot hide it."* That is true of the extension. It is not true of iCloud Keychain on Chrome or of the local GPM passkey, both named in the living requirement as providers that must not be hidden.
- *"Safari and Firefox ignore hints, so the risk is small."* Chrome honours hints and is the most common desktop browser. I have no sign-in analytics for `auth.identikey.me`, so this is an assumption, not a measurement. The manual check in contract item 1 settles it either way.
- *"The steer said 'beside the other hints'."* Today there are no other hints (they are stripped). "Beside" reads as "alongside", not "ahead of". Putting `hybrid` last, or after `client-device`, still carries out Duke's decision.

## Contract I would accept

1. Options include all three hints, with `hybrid` **not first**. Recommended order: `client-device`, `hybrid`, `security-key`. The alternative is that the author records a dated manual check on current Chrome desktop showing that a `hybrid`-first list still offers the local or synced passkey on the first screen.
2. The delta invariant is: the hint list is empty or contains all three values. No single-value or two-value list. `authenticatorAttachment` stays absent. This covers creation **and** request options.
3. Tests cover the four begin paths (registration, discoverable assertion at `ceremonies.rs:225` and `:250`, allow-list assertion at `:219` and `:345`), asserting the exact list and order.
4. The change record names a manual hybrid check (phone OS, desktop browser and version) or says "not verified on hardware".
