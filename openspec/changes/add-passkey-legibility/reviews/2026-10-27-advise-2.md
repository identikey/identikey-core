## Blind pass

These ten lines were persisted in this file after reading the proposal,
living passkeys spec, and cited code, before opening the design, delta,
tasks, or previous review. They are preserved verbatim.

1. Pin this as account presentation work: existing WebAuthn verification, account binding, and signed-out behavior remain authoritative.
2. Pin trimmed nonempty nickname > pinned provider name > Passkey, including missing AAGUIDs and unreadable metadata; refuse any fallback that erases a nickname.
3. Pin AAGUID capture after successful registration verification and keep provider lookup out of ceremony acceptance and authorization.
4. Pin the persisted backup value to registration-time BS, distinct from BE; refuse a label that implies assertion refresh or a current recovery guarantee.
5. Preserve unknown backup state through extraction, insertion, loading, and rendering; refuse coercing missing or legacy NULL values to false.
6. Require an explicit rule for metadata-free insertion and historical false values, since current bool APIs cannot distinguish absence from observed BS=false.
7. Keep the pinned provider list local, optional, and presentation-only; a missing entry, parse failure, or unusable icon must not lose the account or passkey row.
8. Preserve escaping, session scoping, exclusion of key material, and successful-assertion last-used updates without broadening counter policy.
9. Require evidence for real accepted assertions with distinct stored AAGUIDs, plus nickname/fallback and true/false/unknown backup cases; resolver tests alone are insufficient.
10. Tradeoff: accept a compact stale provider list and registration snapshot for bounded scope, provided the UI makes snapshot semantics clear and unknown stays unknown.

## Comparison and steelman

The revised contract answers the material concerns. The delta adds a
presentation requirement and preserves the living spec's verification,
account-binding, OIDC-return, signed-out, and key-material boundaries. The
design correctly names `insert_passkey_with_metadata` as the registration
write. Verification precedes metadata extraction in `ceremonies.rs:181-200`;
ceremony store queries omit presentation AAGUIDs. The account handler scopes
rows to the authenticated XID (`main.rs:514-567`). These support blind-pass
points 1, 3, and 8 without changing authentication policy.

Nickname precedence is now consistent in the design and normative delta:
trimmed nonempty nickname, provider, then “Passkey”. The fallback scenario
requires no nickname, and separate scenarios cover unavailable metadata
and blank nicknames. This answers point 2 and the first prior send-back.
The proposal's Why retains historical wording about dropped metadata, and
its journey still abbreviates unreadable-list fallback to “Passkey”. I read
those against the explicit corrected preparation, What, design, and SHALLs;
they do not override nickname precedence or imply missing registration code.

The design and delta now pin BS rather than BE, explicitly prohibit
assertion refresh, and require missing/legacy backup values to render as
unknown. This answers points 4–5. Snapshot wording must remain visible to
the person reading the eventual row; an unqualified current-status claim
would not express the accepted registration snapshot contract. Exact copy
and representation are implementation choices.

The strongest objection from my blind pass is point 6: the compatibility
wrapper currently supplies false, the parser returns false on missing
metadata, and the loader collapses NULL to false. However, the design calls
the wrapper empty-metadata insertion, and the delta already requires a
missing value to remain unknown. Those rules cover absent metadata through
the whole path, not merely the final rendering branch. They leave no need
for another architecture decision before implementation. A nullable database
column already exists (`migrations/0001_initial.sql:77`). Do not infer unknown
solely from an absent AAGUID: a readable BS=false is a legitimate observation.
Historical false values that have already lost provenance cannot be reliably
reclassified from this column alone; I withdraw any demand for speculative
historical reconstruction or a new provenance subsystem in this slice.

The compact three-provider pin, source URL/date, local lookup, and
missing/unreadable-list fallback answer points 7 and 10. Existing code
escapes labels and permits only embedded SVG data URLs for icons
(`passkey_metadata.rs:45-64`, `pages.rs:184-186`). A live metadata service,
expanded provider coverage, and nickname-editing UI are unnecessary here.

Point 9 is now honestly represented as remaining work. The task requires
real assertions for two valid credentials with distinct stored presentation
AAGUIDs and explicitly rejects store-only evidence. Static separation of
presentation metadata supports the architecture; it does not satisfy that
test. The previous review's evidence objection is reconciled without
pretending the test has run.
